# 与 armcc 的结构性差距：一份诚实的边界说明

> 这份文件回答一个问题：**0.9.1 的十六个 `-fopt-*` 全部打开之后，为什么还是打不过
> armcc？** 答案不是「还差几个 pass」，而是这套代码生成模型自己不产生 armcc 那种
> 代码。本文把差距拆成可核对的行，把「还剩什么能省」写成有上限的量，并明确写出
> **不承诺**什么。
>
> 口径与 `docs/COMPARISON.md` §1 完全相同（95 个有效 TU、Cortex-M4、`-O2`、不含链接
> 期优化、不含库函数），两份文件的差别只在用途：COMPARISON 记「优化项挣了多少」，
> 本文记「挣不到的那部分是什么」。

## 1 结论

| 编译器 | 指令数 | 代码字节 |
| --- | ---: | ---: |
| arkc（十八个 `-fopt-*` 全开） | 14,218 | 36,072 |
| armcc 5.06u7 `-O2` | 5,619 | 13,920 |
| armclang `-O2` | 5,064 | 13,848 |
| armclang `-Oz` | 4,246 | 11,284 |

相对 armcc `-O2` 是 **2.53× 指令 / 2.59× 字节**；相对 armclang `-O2` 是 2.81× / 2.60×，
相对 `-Oz` 是 3.35× / 3.20×。

**一句话**：差的 8,599 条里有 **6,277 条（73%）落在同一组「值运输」类别**里（§3），
剩下的 2,322 条分散在地址计算、比较、分支与屏障。也就是说，这不是「某几个 pass 没写」，
而是**每一个中间值都要过一次寄存器或一次内存**这条模型性代价。

## 2 指令构成（三臂同一语料）

按助记符归类，百分比是占该臂自己总数的比例。分类规则见 §7 的复现脚本：条件码与
`S` 后缀先归一（`MOVS`/`MOVEQ` 都算 `MOV`），`MOV` 再按操作数分成「寄存器到寄存器」
与「立即数」两类。

两条必须先说清楚的读法：

- **armcc 的 `MOVW`/`MOVT` 是 0**，它把 32 位常量放进字面量池（391 条 `LDR [pc]`），
  我们每条常量两次指令。这不是「armcc 更会优化」，是**两种不同的常量物化策略**。
- **armcc 的分支类（22.9%）比我们高**：它的控制流更少被合并，且每个函数结尾都有
  `BX lr`。这一栏我们不欠，反而少 262 条。

## 4 三条结构性原因（每条都对应上面的数）

### 4.1 值栈机：每个表达式节点都真的落一次

后端的表达式求值是一条值栈：压一个值、弹两个值、算完再压回去。`-fopt-vstack` 把
**相邻的** `PUSH`/`POP` 折成寄存器搬运，`-fopt-vreg` 把「每一处提及都是 `LDR`/`STR
[r6, #n]`」的槽提升到 `r8-r11`，两者合起来把帧访问从 3,213 条压到 856 条（−73%）。
但**模型没变**：一个中间值只要活过一条语句边界，就只能去帧槽或池寄存器，于是
`MOV` 立即数 2,003 + `MOV` 寄存器 1,241 + `PUSH`/`POP` 1,239 这三笔仍在原地。
armcc 直接把中间值留在 `r0-r3` 里，它的这三笔合计只有 757 条。

### 4.2 每个中间值过 `r0`

本后端是单累加器式的：任何一次「结果要给下一个节点用」都经过 `r0`（`MOV r0, rX`
在 `BL` 前 3 行内的只有 31 条，其余 345 条是节点之间倒手；`MOV rX, r0` 411 条里只有
66 条紧跟 `BL`）。`PUSH {… r0 …}` 532 条是这条设计的直接账单：值栈把 `r0` 暂存到
栈上，紧接着 `POP {r0}` 的只有 46 条，剩下 486 条都不是「压了又弹」，而是**真的把
中间值存到内存再取回来**。

### 4.3 地址每次重算

`ADD`/`SUB` 1,493 条对 armcc 的 194 条（+1,299）。每次结构体字段访问都重新算
「基址 + 偏移」，没有「基址留在寄存器里、偏移直接进寻址模式」的复用。这一条与 §4.1
同源：基址也是一个中间值，也会被值栈丢回帧里。

## 5 还剩什么能省（有上限的量）

下面四项是**当前二进制上量出来的**，不是估计；每项都写了代价，写在这里是为了让
「要不要做」成为可核对的决定，而不是感觉。

### 5.1 常量池：−803 条 / −2,712 字节（唯一两位数收益）

`MOVW`+`MOVT` 共 803 对（1,606 条），覆盖全语料只有 **125 个不同的 32 位常量**
（平均每个常量被物化 6.42 次）。若改走 pc 相对字面量池，每个使用点一条 `LDR`：

- 指令：1,606 → 803，**省 803 条（−5.6%）**；
- 字节：6,424 → 3,712（803 × 4 + 125 × 4），**省 2,712 B（−7.5%）**。

代价是真实的：池必须**不可被顺序执行**（跳转绕过、或放在函数的 `BX lr` 之后）、
16 位/32 位对齐、链接期重定位（与 `--reloc-data` 的交互要重新写测试）、以及裁切宏
`ARKCC_FEATURE_LITPOOL`。收益上界确定、实现量也确定，**这是当前唯一值得单独立项的
一项**。

### 5.2 `PUSH {… r0 …}` 532 条（3.7%）

其中只有 46 条紧接着 `POP {r0}`。要省掉剩下的 486 条必须改值栈模型（让中间值留在
寄存器），与 §4.1 是同一件事，收益已被 F1 否证线（< 5% 即收档）框住。

### 5.3 常量重复物化 1,865 条（13.1%）

`MOV r0, #imm` 999 + `MOV rX, #imm` 866。这一项与 §5.1 **不能重复计**：池化之后这些
站点大多还会剩一条 `LDR`，真正能省的只有「同一个常量在同一基本块里被物化多次」的部分
（`-fopt-constcache` 已经吃掉 159 条，剩下的没有量过）。

### 5.4 寄存器拷贝 1,241 条（8.7%）

`-fopt-copyprop` / `-fopt-coalesce` / `-fopt-live` 已经清掉跨语句的冗余拷贝，剩下的是
跨基本块边界的活跃性：要再删必须做**块间**活跃性（S6b-2 的范围），收益 < 5%。

### 5.5 登记但不做的两项

- **`DMB SY` 139 条**（armcc 12 条）：每次 `volatile` 写都插一条屏障，armcc 会合并。
  能不能合并要先证「同一序列里相邻的 volatile 写不需要各自屏障」，这是语义问题不是
  优化问题，**未验证前不动**。
- **短条件跳转（`B<cond>` T1）**：本后端恒发 32 位 T3，改 T1 需要布局定点迭代
  （±256 字节），与 `docs/COMPARISON.md` §4 的结论一致：收益与风险不成比例。

## 7 不承诺，以及怎么重测

- **不承诺打到 5,619**。要打到那个数，需要换代码生成模型（值栈 → 图着色式寄存器
  分配 + 常量池 + 基址复用），那是 0.9.2 以后的事；本文不改任何判据，也不关闭任何
  已收档的否证线。
- **本文的所有数字都可以重测**：
  - 指令构成：`D:/tmp/fr/cmpark_keep.py`（arkc 三臂）与 `D:/tmp/fr/cmp_arm.py`
    （armcc/armclang 六臂）产出 `.s` / `.o`，再用 `measure_mix2.py` 归类；
  - 常量池上界：`measure_gap.py`（数 `MOVW`/`MOVT` 配对与不同常量数）；
  - 三臂总计：`cmpark_keep.json` / `cmpark_vreg17.json` / `cmp_arm.json`。
- **这张表不该被读成**「arkc 不可用」：它自己编译自己、编译 HAL、在 STM32H743 与
  F401 上跑过（`docs/BOARD_VALIDATION.md`），语义正确性由 `tests/arm_exec` 逐条执行
  验证。这里只有一个维度：指令数与代码字节。
