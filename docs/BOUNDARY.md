# 与 armcc 的结构性差距：一份诚实的边界说明

> 这份文件回答一个问题：**0.9.1 的十九个 `-fopt-*` 全部打开之后，为什么还是打不过
> armcc？** 答案不是「还差几个 pass」，而是这套代码生成模型自己不产生 armcc 那种
> 代码。本文把差距拆成可核对的行，把「还剩什么能省」写成有上限的量，并明确写出
> **不承诺**什么。
>
> 口径与 `docs/COMPARISON.md` §1 完全相同（95 个有效 TU、Cortex-M4、`-O2`、不含链接
> 期优化、不含库函数），两份文件的差别只在用途：COMPARISON 记「优化项挣了多少」，
> 本文记「挣不到的那部分是什么」。

## 1 结论

| 编译器 | 指令数 | 代码字节 |
| --- | ---: | ---: |
| arkc（十九个 `-fopt-*` 全开） | 13,116 | 34,200 |
| armcc 5.06u7 `-O2` | 5,619 | 13,920 |
| armclang `-O2` | 5,064 | 13,848 |
| armclang `-Oz` | 4,246 | 11,284 |

相对 armcc `-O2` 是 **2.33× 指令 / 2.46× 字节**；相对 armclang `-O2` 是 2.59× / 2.47×，
相对 `-Oz` 是 3.09× / 3.03×。

**一句话**：差的 7,497 条里有 **4,468 条（59.6%）落在同一组「值运输」类别**里（§3），
剩下的 3,029 条分散在地址计算、比较、分支与屏障。也就是说，这不是「某几个 pass 没写」，
而是**每一个中间值都要过一次寄存器或一次内存**这条模型性代价。

## 2 指令构成（三臂同一语料）

按助记符归类，百分比是占该臂自己总数的比例。分类规则见 §7 的复现脚本：条件码与
`S` 后缀先归一（`MOVS`/`MOVEQ` 都算 `MOV`），`MOV` 再按操作数分成「寄存器到寄存器」

两条必须先说清楚的读法：

- **armcc 的 `MOVW`/`MOVT` 是 0**，它把 32 位常量全放进字面量池（391 条 `LDR [pc]`）。
  我们到 0.9.1 之前是每条常量两次指令；`-fopt-litpool` 落地后这一行从 1,740 降到 338，
  并在「字面量池」一行有了 705 条（比 armcc 多 314）。同一策略、不同完成度——剩下的
  338 条（`MOVW` 236 + `MOVT` 102）里，102 对仍成对留着（**96 对**带 `.arkdata`
  链接器补丁），另外 134 条是本来就只需一条 `MOVW` 的 16 位常量，不成对、不在本
  pass 的范围里。
- **armcc 的分支类（22.9%）比我们高**：它的控制流更少被合并，且每个函数结尾都有
  `BX lr`。这一栏我们不欠，反而少 262 条。

**各行相加正好等于合计**：上表十八行相加是 **13,116**，与合计逐条对上。旧版里那 13 条
未归类形态由新的统一口径吃掉（`classify2.py`：`[pc` 一律记池、数据伪指令不计、
条件码与 `S` 后缀先归一、`MOVW`/`MOVT` 单列）。

## 4 三条结构性原因（每条都对应上面的数）

### 4.1 值栈机：每个表达式节点都真的落一次

后端的表达式求值是一条值栈：压一个值、弹两个值、算完再压回去。`-fopt-vstack` 把
**相邻的** `PUSH`/`POP` 折成寄存器搬运，`-fopt-vreg` 把「每一处提及都是 `LDR`/`STR
[r6, #n]`」的槽提升到 `r8-r11`，两者合起来把帧访问从 3,213 条压到 **922** 条（−71%）。
但**模型没变**：一个中间值只要活过一条语句边界，就只能去帧槽或池寄存器，于是
`MOV` 立即数 1,202 + `MOV` 寄存器 1,571 + `PUSH`/`POP` 1,239 这三笔仍在原地（4,012 条）。
armcc 直接把中间值留在 `r0-r3` 里，它的这三笔合计只有 759 条。

### 4.2 每个中间值过 `r0`

本后端是单累加器式的：任何一次「结果要给下一个节点用」都经过 `r0`（`MOV r0, rX`
370 条里只有 16 条落在 `BL` 后 3 行内，其余是节点之间倒手；`MOV rX, r0` 398 条里只有
7 条落在 `BL` 前 3 行内）。`PUSH {… r0 …}` 532 条是这条设计的直接账单：值栈把 `r0`
暂存到栈上，紧接着 `POP {r0}` 的只有 46 条，剩下 486 条都不是「压了又弹」，而是
**真的把中间值存到内存再取回来**。

### 4.3 地址每次重算

`ADD`/`SUB` 1,493 条对 armcc 的 302 条（+1,191）。每次结构体字段访问都重新算
「基址 + 偏移」，没有「基址留在寄存器里、偏移直接进寻址模式」的复用。这一条与 §4.1
同源：基址也是一个中间值，也会被值栈丢回帧里。

## 5 还剩什么能省（有上限的量）

下面四项里**第一项已经做完并量过**（`-fopt-litpool`），其余三项仍是**当前二进制上
量出来的**待做项——不是估计；每项都写了代价，写在这里是为了让「要不要做」成为可核对
的决定，而不是感觉。

### 5.1 常量池：−705 条 / −1,134 字节（**已实现**，`-fopt-litpool`）

这一项上一版估的是「−803 条 / −2,712 B」，现在**做完了、量过了**，实测是
**−705 条 / −1,134 B**（95 TU：14,271 / 36,114 → **13,566 / 34,980**）。与文档
[LITPOOL.md](LITPOOL.md) 是同一份读数，这里只留结论与差额解释：

- 十八开关下相邻同寄存器 `MOVW`/`MOVT` 对共 **807**；其中 **96** 对带 `.arkdata`
  标记（链接器要打两个半字补丁，不能改成 `LDR`）、**0** 对异寄存器或不相邻，可池化
  **711**，其中**实际转换 705**（余 6 对落在本 pass 拒绝的大函数/长区域里），与指令
  差逐条对上。
- 字节账：705 个站点各省 4（**−2,820**）、359 个池各占 4（**+1,436**）、每个池前的
  `.align 4` 合计补 250（**+250**）⇒ **−1,134**，与实测逐字节对上。
- 与旧估值的差（−803 vs −705）来自三处：不可动的 `.arkdata` 对、被本 pass 拒绝的
  长区域，以及**每个区域组各建一个池**（同一常量在不同组里各占一份），后者正是为了
  让 `LDR [pc, #imm]` 的 4,095 字节可达范围罩得住大函数。

所以「唯一两位数收益」这个判断是对的，但它的实际大小比估算小 13%。设计、拒绝清单、
区域切分与 21 项门禁见 [LITPOOL.md](LITPOOL.md)；**本条已从「待做」改为「已做」**。

### 5.2 `PUSH {… r0 …}` 532 条（4.1%）

其中只有 46 条紧接着 `POP {r0}`。要省掉剩下的 486 条必须改值栈模型（让中间值留在
寄存器），与 §4.1 是同一件事，收益已被 F1 否证线（< 5% 即收档）框住。

### 5.3 常量重复物化 1,202 条（9.2%）

`MOV r0, #imm` 1,052 + `MOV rX, #imm` 150。这一项与 §5.1 **不能重复计**：池化之后这些
站点大多还会剩一条 `LDR`，真正能省的只有「同一个常量在同一基本块里被物化多次」的部分
（`-fopt-constcache` 已经吃掉 159 条）。

**实测上界（2026-11-24，先量后收档）**：按「同一基本块内、同一个立即数第二次及以后
才物化」的口径数十九开关语料：`MOV rX, #imm` 共 **1,540** 条（含 `#0`、尾声的返回码等，
比上面 1,202 的分类口径宽，因此上界只会偏大），其中同块重复 **237** 条；池化后的
`LDR rX, .Llit_*` 共 705 条，其中同块重复引用同一池标签 **87** 条。两者相加
**324 条 = 全部指令的 2.47%**，而且这是**天花板**——真正能删还要目标寄存器在那一行仍
持有该值（要活跃性），实际只会更少。按 F1（< 5% 即收档）**收档**，不再做同块常量复用。

> 记一句给后来者：`-fopt-constcache` 的门槛是「一个函数里出现 ≥5 次」，它已经覆盖了
> 真正值得压寄存器的形态；剩下的是块内一两处重复，省一条 `MOV` 要付一次活跃性分析的
> 复杂度，收益 2.5% 上限，不划算。

### 5.4 寄存器拷贝 1,571 条（12.0%）

`-fopt-copyprop` / `-fopt-coalesce` / `-fopt-live` 已经清掉跨语句的冗余拷贝，剩下的是
跨基本块边界的活跃性：要再删必须做**块间**活跃性（S6b-2 的范围）。

**实测上界（2026-11-24，先量后收档）**：把每条 `MOV rD,rS` 放进「基本块内剩余读 + 跨块
`live_out`」的口径里数（脚本口径自检：全语料 95 TU 数出 13,116 条指令、1,571 条
`MOV rD,rS`，与 §2/§5.4 的分类器读数逐条相同），其中「目标只被块外消费者用、块内之后
再无人读」的只有 **245 条（占全部指令 1.87%，占寄存器拷贝本身 15.6%）**。这是**上界**
（不确定的一律算活），按 F1（< 5% 即收档）**收档**，S6b-2 不实现。剩下 1,326 条拷贝在
块内就有消费者，删它们要改值栈/分配模型，不在寄存器拷贝这一项里。

**另一条更弱的路也量过了**：「`MOV rD, rS` 后面紧跟一条只读 `rD`、且 `rD` 在本块之后
不再被读」的折叠（把源寄存器直接塞进下一条指令，`CMP r0, #0` → `CMP r5, #0`）只有
**32 条 = 0.24%**，同样按 F1 收档。两条加起来仍不到 5%，所以寄存器拷贝这一栏除了
值栈模型没有别的可做——`-fopt-copyprop` 的 B 规则（紧跟 `OP rD, rD, X`）已经吃掉了
真正成形的部分。

### 5.5 登记但不做的两项

- **`DMB SY` 139 条**（armcc 12 条）：每次 `volatile` 写都插一条屏障，armcc 会合并。
  能不能合并要先证「同一序列里相邻的 volatile 写不需要各自屏障」，这是语义问题不是
  优化问题，**未验证前不动**。
- **短条件跳转（`B<cond>` T1）**：本后端恒发 32 位 T3，改 T1 需要布局定点迭代
  （±256 字节），与 `docs/COMPARISON.md` §4 的结论一致：收益与风险不成比例。

## 7 不承诺，以及怎么重测

- **不承诺打到 5,619**。要打到那个数，需要换代码生成模型（值栈 → 图着色式寄存器
  分配 + 常量池 + 基址复用），那是 0.9.2 以后的事；本文不改任何判据，也不关闭任何
  已收档的否证线。
- **本文的所有数字都可以重测**：
  - 指令构成：`D:/tmp/fr/cmpark_keep.py`（arkc 三臂）与 `D:/tmp/fr/cmp_arm.py`
    （armcc/armclang 六臂）产出 `.s` / `.o`，再用 `classify2.py` 归类（统一口径：
    `[pc` 记池、数据伪指令不计、条件码与 `S` 后缀归一、`MOVW`/`MOVT` 单列）；
  - 常量池上界：`measure_gap.py`（数 `MOVW`/`MOVT` 配对与不同常量数）；
  - 常量池实测：`D:/tmp/fr/cmpark_lp.py`（十八 / 十九开关两臂，产出
    `cmpark_lp.json` 与 `cmpark_lp/*_all18.s|*_all19.s`）；
  - 三臂总计：`cmpark_keep.json` / `cmpark_vreg17.json` / `cmp_arm.json`。
- **这张表不该被读成**「arkc 不可用」：它自己编译自己、编译 HAL、在 STM32H743 与
  F401 上跑过（`docs/BOARD_VALIDATION.md`），语义正确性由 `tests/arm_exec` 逐条执行
  验证。这里只有一个维度：指令数与代码字节。
