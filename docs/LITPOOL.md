# 32 位常量进字面量池（`-fopt-litpool`）

[English](LITPOOL.en.md) | 中文

> 0.9.1 的第二条优化（承接 [DIVCONST.md](DIVCONST.md)）。一句话：**把一个 32 位常量
> 的「`MOVW` + `MOVT` 两条指令」换成「从 PC 相对字面量池里 `LDR` 一条」**。`MOVW`+`MOVT`
> 是 8 字节的代码搬 4 字节的值；池化后每个使用点 4 字节，加上池里那 4 字节。
>
> 实现位置：`src/backend/arm/backend_arm.c`（`ark_litpool_function()`，**文本级 pass**）
> 新增汇编器形式：`LDR rd, <label>`（单条 32 位编码）
> 门禁：`tests/run_litpool_tests.py`（`make test-litpool`，21 项）
> 开关：`-fopt-litpool` / `-litpool`，INI `opt-litpool=` / `litpool=`

---

## 1. 收益模型：`4(c - 1)`

一个 32 位常量被使用 `c` 次：

| 方案 | 代码量 |
| --- | --- |
| `MOVW`+`MOVT`，每处一份 | `8c` 字节、`2c` 条指令 |
| 字面量池，池里一份 | `4c + 4` 字节、`c + 1` 条指令 |

节约 `4(c - 1)` 字节、`c - 1` 条指令。

两条直接推论，写在这里以免被误读：

- **`c = 1` 是字节中性的**（4 + 4 = 8），只是少一条指令。所以本 pass **不按使用次数
  筛**：单次使用的常量也池化，收益是「一条指令」，不是尺寸。
- **`c = 0` 不存在**（没被使用就不会有 `MOVW`/`MOVT`），故不会出现负收益。

真实语料上「同一个 32 位常量被物化多次」很普遍：95 TU 里 807 个 `MOVW`/`MOVT` 对
覆盖的常量只有 125 个左右量级（旧估算是 6.42 次/常量），池化正是吃这部分。

## 2. 为什么是文本级 pass，不是新的 IR pass

理由与 `-fopt-cmat`、`-fopt-slotreg` 一致：

- **它要看最终的寄存器名**。池装载是 `LDR rD, <label>`，`rD` 必须是分配之后的名字；
  在 IR 上做就要把寄存器分配结果再搬回来。
- **它必须跑在 `-fopt-cmat` 之后**。cmat 的 M1/M2 已经把「常量已经在一个寄存器里」和
  「常量折进寻址方式」这两种情形吃掉了，剩下才是真的需要内存里有一份值。若在其之前池化，
  会把 cmat 本来能折掉的站点变成一条 `LDR`，白亏一条。
- **它必须跑在所有会改文本的 pass 之后**（`-fopt-vreg`、`-fopt-slotreg`、`-fopt-cmat`）：
  这些 pass 会插入/删除行，插池之后再删行会让池标签与站点距离变化——虽然本 pass 用
  `LDR rd, <label>` 让距离不影响编码，但站点被删掉会留下没人引用的池。

pass 顺序（`ark_emit_program`）：vstack → addr → cbz → peep → copyprop → live/coalesce
→ regalloc（内含 constcache）→ vreg → slotreg → cmat → **litpool** → `ark_fix_far_offset`
→ `.init_array` / `.fini_array` → `__arkcc_init_globals`（单独发射，不经过任何文本 pass）。

## 3. 新增的汇编器形式：`LDR rd, <label>`

内部汇编器原先支持 `LDR rd, =label`，它会展开成 `MOVW` + `MOVT`——那正是本 pass 要消灭的
形状，用不了。于是新增了第二种形态：

```
    LDR  r3, .Llit_7_2_0
```

- **固定 32 位编码**：`hi = 0xF8DF`、`lo = (rd << 12) | imm12`，即 `LDR Rt, [PC, #imm]`，
  `pbase = (pc + 4) & ~3`（Thumb 的 PC 读作「当前指令 + 4」，再按字对齐），`imm12` 是
  0..4095 的**字节**偏移。
- **为什么长度固定**：pass1 统计尺寸时还不知道池与站点的距离（池在函数末尾才生成），
  若按距离在 16/32 位之间浮动，pass1 与 pass2 的尺寸必然分歧，标签地址全部错位。
  固定 32 位是最省事且正确的选择，代价是每个站点 4 字节——这正好就是收益模型里的 4。
- **越界即报错，不静默截断**：`imm12 > 4095` 或标签不在本文件时，
  `diag_tool(DIAG_SEV_ERROR)` 报错并在原位发两条 `0xBF00`（`NOP`）占住 4 字节，
  保证尺寸不变、后续标签地址仍然正确。**宁可报错，不给错答案。**

## 4. 池放在哪里：区域化，而不是「函数末尾一个池」

`LDR [pc, #imm]` 的 `imm12` 只有 4,095 字节 —— 约 1,000 条指令。**一个大函数装不下一个池**
（95 TU 里就有两个这样的函数，它们单独占掉 711 个可转换对中的 225 个）。所以文本被切成
**区域（region）**，按区域建池：

1. **区域边界 = 终止控制流的指令**：`POP {..., pc}`、`BX ...`、无条件 `B ...`。
2. **只认无条件形式**。`POPNE {.., pc}` 之后控制流还会回来，`BXEQ lr` 也是；
   `lp_ends_flow()` 因此要求 `BX`、`POP` 之后紧跟空格/制表符（排除 `BXNE`、`POPNE`）。
   这条是硬约束：池是数据，控制绝不能顺序走进它。
3. **向前贪心合并**：相邻区域拼起来不超过 `LP_REACH_INS = 800` 条指令就并进同一组。
   800 的理由是 `4 × 800 + 4 × 128 = 3,712 < 4,095`，给池前的 `.align 4` 留余量。
4. **单个区域自己就超 800 条 ⇒ 整段不池化**。安全第一：一个没有终止指令的直线区域
   里无处安放池，跳过它只是少省一点，「正确但不够紧」。
5. **池紧跟在它那一组的终止指令之后**，前面一条 `.align 4`。因为终止指令之后控制已经
   离开，而所有分支都跳标签、所有标签都在池之后，所以**没有分支能落进池里**。

## 5. 拒绝清单

| 拒绝 | 原因 |
| --- | --- |
| 函数最后一条指令不是终止指令 | 池是数据；函数若会「掉出末尾」本身就是 bug，加数据会把这个 bug 变成跳进常量 |
| `MOVW`/`MOVT` 对的前一行是 `.arkdata` / `.arkdatasym` | 链接器要给这两条半字打补丁（reloc type 6/15），对必须成对留着 |
| 单个区域 > `LP_REACH_INS`（800 条） | 无处安放池，跳过 |
| 一个池里不同常量超过 `LP_MAX_POOL`（128）个 | 该站点保持原样（`MOVW`/`MOVT` 不动） |
| 整个函数超过 `LP_MAX_LINES`（4096）行 | 整函数放弃（静态表上限；正确但少省） |

第三条与第五条都是**功能上限**而不是保守猜测：表是静态数组（STM32_MIN 剖面下这些
数组整块不编进去，见 §7），不做动态分配。

## 6. 实测（0.9.1-wip，宿主构建，95 个有效 TU，Cortex-M4）

| 读数 | 十八开关 | 十九开关（+`-fopt-litpool`） | 差 |
| --- | ---: | ---: | ---: |
| 指令数 | 14,271 | **13,566** | **−705** |
| 代码字节 | 36,114 | **34,980** | **−1,134** |

- **指令** −705 条（−4.94%），**字节** −1,134 B（−3.14%）。

字节账能逐项对上（`grep -c` 数十九开关产生的 `.s`）：**705 个站点**（`LDR rD, .Llit_*`）
与 **359 个池**（`.Llit_*:` 定义）。每个站点 8 → 4 字节省 4，共 **−2,820**；每个池
占 4 字节，共 **+1,436**；所有池前的 `.align 4` 合计补 **250** 字节。所以

```
-2,820  +  1,436  +  250  =  -1,134  B   （与实测逐字节对上）
```

即：**池越少越省**——这就是区域贪心合并（每组一池，而不是每个终止指令一池）的原因。

配对审计（同一语料，`MOVW rX` 紧跟 `MOVT rX`）：

| 项 | 数 |
| --- | ---: |
| 十八开关下相邻同寄存器 `MOVW`/`MOVT` 对 | **807** |
| 其中被 `.arkdata` 标记、链接器要打补丁 | 96 |
| 其中非同寄存器或不相邻（不是一对） | 0 |
| 可池化（`807 − 96`） | 711 |
| **实际转换** | **705**（另 6 对落在本 pass 拒绝的长区域/大函数里） |
| 十九开关下剩余 `MOVW` / `MOVT` | 236 / 102（合计 338 = 1,740 − 1,402） |

`807 − 96 = 711` 可池化，实际转换 705，与实测指令差**逐条对上**。旧版
`docs/BOUNDARY.md §5.1` 曾按「803 对全部转换、每个常量只建一份」估成 −803 条 /
−2,712 B；实测比估算小，差值由三部分解释：96 对是链接器补丁（不能动）、6 对被区域/
函数上限拒绝、以及**每个区域组各建自己的池**（同一常量在不同组里各占一份，`c` 次有效
使用摊薄了）。

单函数示例 `HAL_RCC_OscConfig()`（`stm32f4xx_hal_rcc.c`）：

| 口径 | 该函数指令数 | 该 TU 总计 |
| --- | ---: | ---: |
| 十八开关 | 1,256 | 2,171 |
| 十九开关 | **1,229** | **2,085** |

这个函数长到必须切成 4 个组，正好是区域化机制在真实代码上的证据。

## 7. 裁剪（三层，默认关时零变化）

| 层次 | 手段 | 关掉时的保证 |
| --- | --- | --- |
| 编译期 | `ARKCC_FEATURE_OPT_LITPOOL`（`include/arkcc_config.h`；`ARKCC_PROFILE_STM32_MIN` ⇒ 0） | pass 与全部静态表整块消失，`enable_opt_litpool` 的引用折叠掉 |
| 运行期 | `g_config.enable_opt_litpool`，`-fopt-litpool` / `-litpool`，INI `opt-litpool=` / `litpool=` | 默认 **0**；不开时产物与「不含该特性」的构建逐字节相同（门禁实测） |
| 剖面 | 无需（文本级 pass，`--pipeline` 阶段表不登记） | — |

**静态表占内存**：`LP_MAX_LINES = 4096` ⇒ 七张行表 4096 × (4+4+4+2+2+4+4) ≈ 96 KB，
加三张 1,024 项的组表 ≈ 12 KB、池表 512 B，合计约 **108 KB**。这在 PC 上无所谓，在 STM32H743 的 RAM 上不小，所以板端剖面
（`ARKCC_PROFILE_STM32_MIN`）**默认裁掉**；宿主与 Linux/Windows 交叉构建保留。

裁剪构建**拒绝**选项而不是装作优化：`-DARKCC_FEATURE_OPT_LITPOOL=0` 时
`-fopt-litpool` 报

```
Fatal error: C3900U: -fopt-litpool is not compiled into this build
(rebuild with -DARKCC_FEATURE_OPT_LITPOOL=1)
```

且不带旗标时编译行为与完整构建一致（门禁第 6 组）。

## 8. 门禁（`tests/run_litpool_tests.py`，21 项）

`make test-litpool`。夹具与断言：

1. **OFF IS OFF**：不开旗标与裁切构建（`-DARKCC_FEATURE_OPT_LITPOOL=0`）产出的 `.s`
   逐字节相同。
2. **重复常量（`REUSE`）**：同一常量 3 处 + 另 1 对 ⇒ 指令减少量 == 该夹具内相邻同寄存器
   `MOVW`/`MOVT` 对数；镜像（`ARKOBJ2` 头）变小。
3. **单次使用（`ONCE`）**：每条材料化少一条指令，**字节不变**（8 → 4 + 池 4）。
4. **池位置**：每个池由 `.align 4` 引出，且紧前面的指令是终止指令。
5. **标签唯一且自洽**：每个 `.Llit_` 定义唯一；每个站点引用的标签都已定义。
6. **多区域（`region_src(80)`，约 3,000 条 / 79 个池 / 4 个组）**：至少有 2 个池，
   且至少一个落在函数中部（不是只挂在结尾）；仍然汇编通过（reach 门禁）。
7. **`.arkdata` 不动**：`--reloc-data` 下唯一的 `MOVW`/`MOVT` 是链接器补丁对，
   `.arkdata` + `MOVW` + `MOVT` 三元组逐字节不变，整个函数 30/30 行不变。
8. **执行三方一致**：三个夹具在 off / on / 「仅 on」三种构建下于 unicorn 上跑出的结果
   等于 Python 期望值。
9. **裁切门禁**：`-DARKCC_FEATURE_OPT_LITPOOL=0` 的构建以 `C3900U` 拒绝
   `-fopt-litpool`，不带旗标仍能编译。
10. **选择性**：同一 TU 里的常量材料化被改写，变量与 `.arkdata` 对被保留——排除
    「整个文件其实没跑过」的假绿。

另跑执行级全套：`tests/arm_exec/run_arm_exec.py --arkcc ./arkcc.exe --extra=-fopt-litpool`
⇒ **0 failure(s)**；`run_cmat_tests.py`、`run_vreg_tests.py` 全绿。

## 9. 与 `-fopt-constcache` 的分工

两者都处理「同一个 32 位常量反复物化」，但机制不同，**不是替代关系**：

| | `-fopt-constcache` | `-fopt-litpool` |
| --- | --- | --- |
| 值放在哪 | callee-saved 寄存器（`r8`–`r11`） | 内存里的字面量池 |
| 使用点成本 | `MOV rD, rC`（2 字节） | `LDR rD, [pc, #imm]`（4 字节） |
| 前置成本 | 入口一次 `MOVW`+`MOVT` + 保存/恢复寄存器 | 池里 4 字节（无运行时指令） |
| 触发门槛 | 同一函数里 ≥5 次 | 无门槛（`c ≥ 1` 即做） |
| 冲突 | 寄存器不够就放弃 | 无寄存器需求 |

理论上「先 constcache 吃高频常量、再 litpool 吃剩下的」收益更高，但 constcache 抢走的
常量在池里本来也是一份，且两者对同一常量同时生效会让 constcache 那 2 字节的 `MOV`
反而比池 `LDR` 便宜——顺序固定为 **constcache 先、litpool 后**（pass 顺序里 regalloc
在 litpool 之前），池只吃 constcache 没接的站点。这也是实测收益小于「理论上界」的原因之一。

## 10. 刻意没做的事

- **不做汇编器级池**（`.ltorg` / 自动收集 `LDR =imm`）：代码生成侧才知道哪个常量值得进池、
  哪个组该建池；汇编器级方案会把池放在任意位置，且无法参与区域的 4,095 字节预算。
- **不做跨函数共享池**：那需要链接期配合与段布局，且共享池一旦不可达就成死重量。
- **不用 16 位 `LDR`（T1，`imm8 × 4`）**：可达距离只有 1,020 字节，区域会碎成
  每 250 条一个池，池本身的开销（每个常量 4 字节）把收益吃掉；且 T1 只能落 `r0`–`r7`。
- **不动 `.arkdata` 对**：见 §5。
- **不做「池化后指令变短」的承诺**：单次使用的常量**字节中性**，只少一条指令；
  文档与门禁都按这个口径写。
- **不给 x86-64 / RISC-V 后端做**：那两个后端没有这个取舍，`-fopt-litpool` 在那里是
  无害空操作。
