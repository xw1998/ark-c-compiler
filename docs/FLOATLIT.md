# 浮点字面量的精确转换（单次舍入，宿主与板端同一份实现）

[English](FLOATLIT.en.md) | 中文

> 0.9.1-wip 的「错答案」修复之一。一句话：**一个字面量在源码里写的是一个确定的
> IEEE-754 值（最近值、平局取偶），编译器必须给出这个值，一位不差**。旧词法器把数字
> 一位一位累加进 `double`，每一步都在舍入，长尾数上会差 1 ulp。
>
> 实现位置：`src/lexer.c`（`lit_from_decimal` / `lit_from_hex` / `lit_round`，
> 约 390 行，`static`，单线程）
> 门禁：`tests/run_floatlit_tests.py`（`make test-floatlit`，419 例）
> 开关：**无**。这不是优化，是把「近似」换成「精确」；板端裁切剖面照常编译同一份代码。

---

## 1. 症状：两个 1 ulp 的错答案

```
double a = 123456789012345678.0;          // 发射 0x437b69b4ba630f36，应为 ...0f35
double b = 0x1.0000000000000800000001p0;  // 发射 0x3ff0000000000000，应为 ...0001
```

后者尤其难被发现：值就是 `1.0`，而正确结果只是比它大 1 ulp。两者都是**静默的错答案**
——编译成功、运行成功、结果错一个最低位。按本项目的纪律（「宁可报错，不给错答案」），
这比拒绝编译更糟，所以它排在同期那个 96 字节的体积清理之前做。

反过来，下面这些**不是** bug，是正确结果，写在这里免得下次又被当成 bug 去「修」：

| 字面量 | 正确值 | 说明 |
| --- | --- | --- |
| `0x1.fffffffffffff8p0` | `2.0` | 恰好落在 `1.111…1 × 2^0` 与 `1.0 × 2^1` 的中点，取偶 ⇒ 进位到 2.0 |
| `9e18` | `0x43df399b1438a100` | 短尾数，旧实现也是对的 |
| `0x1p1024` | `inf` | 超出 binary64 上限，按 C 的翻译期溢出处理 |

## 2. 旧实现错在哪

三处，都是「中途舍入」：

1. **十进制、无指数**：`intp = intp * 10.0 + digit`，小数部分
   `fracp = fracp * 10.0 + digit; scale *= 10.0`，最后 `intp + fracp / scale`。
   每一位都在 `double` 里舍入一次，19 位以后必然漂移。
2. **十进制、有指数**：走宿主 `strtod`（正确），但板端没有 libc，那条分支在
   `ARKCC_STM32` 下退化成 `pow(10.0, e)` 乘法——两条路径给出不同答案，而**板端那条才是
   主战场**。
3. **十六进制**：`fpart = fpart * 16.0 + digit`、`e *= 2.0`，同样的逐步舍入。

## 3. 新实现：定点大数，最后一次舍入

思路是把「写出来的十进制/十六进制数」先变成一个**精确的整数 × 2 的幂**，再一次性舍入到
目标格式。全程整数运算，不出现中间浮点值，所以不可能有双重舍入。

- 缓冲区：`LitBig` = 72 个 `unsigned int` = **2304 bit**，五个（`lit_M` 数字、
  `lit_num` / `lit_den` / `lit_quo` / `lit_rem` 做除法）。
- 十进制：
  - `E10 >= 0`：`M × 10^E10`，按 `10^9` 一块乘进去（`lit_mul_add`）。
  - `E10 < 0`：`M / 10^k = (M / 5^k) × 2^-k`。`5^k` 用 `5^13` 一块乘出来，然后
    **二进制逐位长除**（`lit_divmod`）。红利先左移，让商带 56 位——这样末次舍入看到的
    guard/sticky 位是真的 guard/sticky，而不是「商不够长碰巧舍对」。
  - 结果是 `商 × 2^(-t-k)`，`sticky` 取「除法有余数」。
- 十六进制：`0x1.abc p±e` 本身就是 `整数 × 2^(e - 4×小数位数)`，纯移位，不需要除法。
- 舍入：`lit_round(neg, num, e2, sticky, prec)`，最近值、平局取偶，一次到位。
  `prec = 53` 走 binary64（`emax 1023 / emin -1022 / 粒度 2^-1074`），
  `prec = 24` 走 binary32（`127 / -126 / 2^-149`），两次都用同一套代码，只在
  规格化与指数偏置上分叉。

### 3.1 为什么 `float` 后缀也走 prec=24

`float f = 0.1f;` 若先按 binary64 舍入、再转 binary32，就是**双重舍入**：存在十进制串
使第一次舍入把值推到第二次舍入的中点另一侧，最终差 1 ulp（经典反例是
`1.0000000596046447753906251`）。这条路整类消掉，代价只是一次 `prec=24` 的调用。

实测 6 万随机 binary32 用例与精确有理数舍入的结果**零差异**（说明语料里碰不到反例），
但这类「碰不到」不构成保证，所以仍然按单次舍入实现。

### 3.2 上限与如实声明

| 参数 | 值 | 后果 |
| --- | --- | --- |
| `LIT_MAXDIG` | 400 位（十进制或十六进制有效位） | 超出部分不再乘进大数，只记 `sticky` 与位数 |
| 指数累加 | 封顶 100000 | 再大也仍是 `inf` / `0`，判定不受影响 |
| 十进制量级预判 | `> 310` ⇒ `inf`，`< -330` ⇒ `0` | 粗到 ±1 个十进位，只用于跳过无意义的 5^k 计算 |

**只有在「源码写了超过 400 位有效数字、且被截断的部分恰好让值落在舍入中点上」时，
理论上才可能差 1 ulp。** 这个条件写在这里而不是藏在代码里：它是本实现唯一的近似点，
`400` 位已经远超任何真实代码里的字面量长度（2304 bit ≈ 693 位十进制，400 位留了余量）。

## 4. 板端代价

这段代码要跟着 arkc 一起放进 STM32H743 的固件（`mdk/STM32H743_ArkCC/ArkCC.uvprojx`
直接编译 `..\..\src\lexer.c`，与宿主同一份源码，没有 feature 宏）：

| 项 | 读数 | 说明 |
| --- | --- | --- |
| `.bss` | **1,464 B** | 5 × 292 B（`LitBig`）+ 4 B（`lit_overflow`） |
| `.data` | 0 | 没有初始化表 |
| 栈 | 0 | 五个缓冲区是 `static`，不占栈——板端应用栈只有 4 KB，一个 `LitBig` 就 292 B，放栈上五块会直接压垮 |
| libc | 不需要 | 不用 `strtod`、不用 `pow`、不用 `long double` |
| 中间运算 | 全整数 | 只有最后 `union` 装位型时才出现浮点类型；`lit_round` 返回 `double` 是为了调用方直接拿值 |

实测（改动前后各构建一次，同一套工具）：

| 构建 | 读数 | 差值 |
| --- | --- | --- |
| 宿主 x86-64，`gcc -O2` 单独编 `lexer.c` | `.text 14,504 → 18,180`、`.bss 0 → 1,632` | `+3,676 B` / `+1,632 B` |
| 板端剖面 `tools/stm32_build_check.py --layout sdram`（armclang + armlink，真实内存布局） | `code 346,042 → 349,466`、`ro 33,162 → 33,014`、`zi 84,452 → 85,916` | **`+3,424 B` 代码、`−148 B` rodata、`+1,464 B` zi** |

`zi` 的增量正好是 1,464 B —— 就是那五个 `LitBig` 加一个 `int`，一位不差；flash 占用
18.1% → 18.2%，两种布局（`sram` / `sdram`）的 8 项检查全 PASS。

**95 TU HAL 语料逐字节不变**（405,426 B，`asm_sw23` 改动前后完全相同）：语料里没有
长尾数字面量，所以这项修复对现有产物是零字节代价，只在真出现长字面量时才多花那几微秒。

## 5. 门禁

`tests/run_floatlit_tests.py`（`make test-floatlit`，419 例，纯编译 + 汇编文本解析，
不需要 unicorn）：

- 用例：39 个手工硬例（22 十进制 + 9 十六进制 + 8 binary32：两个回归、次正规数边界、
  平局、溢出、超长尾数、`16777217.0f`、`0x1p-149`），外加 220 个随机十进制、80 个随机
  十六进制、80 个随机 binary32 —— 合计 419 例。
- 判法：从生成函数体里找它**实际引用的** `LDR r0, =.L_dbl_k`，再去比对该池条目的
  两个 `.word`。所以「池编号错了」「函数体引了别的常量」都会红。
- 三条防假绿自检：
  1. 用例表必须先跟**旧的累加器**（脚本里照抄了一份 `naive_decimal`）比，至少有一例不同
     ——否则这张表根本抓不到它存在的理由；
  2. binary32 的独立参考实现（`Fraction` 精确舍入）必须先复现四个已知位型；
  3. 每个函数都必须有池引用，池「悄悄空了」算红，不算「没东西可比」。
- 负字面量：词法器只看到数字，符号在运行时修（`EOR r0, r0, #0x80000000`）。所以门禁
  对 `-x` 判两件事：池里是**幅值**的正确位型，且函数体里**确实有**这条符号修正。

### 5.1 独立对拍

把同一份实现单独编成一个宿主程序（`litref`），用 Python 的
`float()` / `float.fromhex()` / `Fraction` 正确舍入做参考，跑随机用例：

| 批次 | 用例数 | 差异 |
| --- | --- | --- |
| binary64 随机十进制（含负号、`e`/`E`、±345 指数、1..25 位尾数） | 59,236 | **0** |
| binary64 随机十六进制（含负号、`p` 指数 -1090..1050） | 60,000 | **0** |
| binary32 随机十进制（`Fraction` 精确舍入为参考） | 59,313 | **0** |
| 合计（种子 7） | **178,549** | **0** |
| 合计（种子 8） | 178,552 | **0** |

（生成 60,000 一档，少数几个用例的距离串短于宿主探针的行过滤阈值，未进比对，
表里记的是实际比对条数。）

边界专测（`.5`、`5.`、`00012.5`、`-0.0`、`0e999999999`、`1e±1000000`、
`0x1p-1074`、`0x3p-1075`、`0x1p1024`、`0x1.fffffffffffffp1023`）全对：
溢出给 `inf`，下溢按舍入给 `0` 或最小次正规数，`-0` 的符号位保留。
