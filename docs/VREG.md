## 2 为什么不能再用文本层

三条已经做过的尝试，都是同一堵墙：

1. `-fopt-slotreg`（P17）：不带安全闸能删 −1.82%，但 5 个 `arm_exec` failure
   （`memcpy` 在内部间接读，文本层看不见）。带闸只剩 −0.34%，**收档**。
2. `-fopt-constcache`（P18/S3a）与 **S3b**：S3b 想省「跨调用活着的值」，
   实测 95 个 TU 里真实机会只有 **5 对 / 0.11%**，**收档**。
3. `-fopt-coalesce`（L5）：81/95 个 TU 逐字节不变，−1.93%；剩下的拷贝一律卡在
   「段内有 `BL`」或「源在段内被写」。

结论：**文本上看不见「这个值此刻在哪个寄存器里」**，所以每一条规则都必须先把
「看不见的读写」当成危险来防——防到安全时收益就没了。要有下一层收益，必须让
「值住在哪个寄存器」成为编译器里的**一等对象**，而不是事后猜。

## 3 目标模型

现在的模型（`docs/RA_VSTACK.md` §1）：IR 是栈机，发射期每个中间值 `PUSH`/`POP`，
`-fopt-vstack` 事后把相邻往返折成 r0/r5/r7 的搬运，其余落回帧。

目标模型：

```
irgen（不变） → IR（不变） → 新的 IR→文本发射器（S6） → 汇编（不变）
                                  ↑
                      虚拟寄存器 + 线性扫描 + spill
```

- **虚拟寄存器**：`IR_PUSH` 与产生值的指令在 S6 里得到一个 `vreg`，不再隐含 r0；
  栈语义由 `vreg` 编号的活跃区间表达，不再有 `PUSH`/`POP` 的机器栈含义。
- **寄存器池**：
  - caller-saved `r0`–`r3`：块内、且活跃区间不跨 `BL` 的值；
  - callee-saved `r8`–`r11`：活跃区间跨 `BL` 的值，代价是每函数一次 `PUSH` 加宽
    （与 `ark_regalloc_function()` 共用同一段保存块，**只允许一个所有者**，
    这条约束在 `docs/OPERAND_ALLOC.md` §4 已经写死）。
  - `r6` 仍是帧基址（不把它交出去：取消帧指针实测只值 0.2%）。
- **活跃区间**：按 IR 线性序 + 基本块（`src/mir.c` 已有 CFG）计算，块边界按
  succ 合并；`RETURN` / `BL` / 间接调用是切分点。
- **spill**：只在 S6c 引入；溢出到帧槽，槽位由 `alloc_local()` 同一套分配器给。
- **与 `-fopt-vstack` 的关系：二选一**（`docs/OPTIMIZER_PLAN.md` P12 S5 的原判）。
  S6 一旦并线，`-fopt-vstack` 的文本重建在同一函数上不再运行；默认保留谁由语料实测决定，
  另一条留作回退开关。

## 5 冻结门禁（实现前不改）

1. **OFF IS OFF**：`-O2` 与 `-O2 -fno-opt-vreg` 逐字节相同（95/95 TU）；
2. **只减不增**：任一 TU 指令数变大即红，不做「平均更好」的解释；
3. **默认关**：`enable_opt_vreg = 0`，INI/CLI 双向可开关；
4. **执行级同值**：`tests/arm_exec/run_arm_exec.py --extra=-fopt-vreg` 全量 0 failure，
   且每条断言仍是「程序外算出的常量」，不允许改成自证；
5. **裁剪拒绝**：`-DARKCC_FEATURE_VREG=0` 的构建以
   `Fatal error: C3900U: -fopt-vreg is not compiled into this build` 拒绝并返回 1，
   不带旗标仍能编译；
6. **板端体积**：`tools/stm32_build_check.py --layout both` 仍全 PASS（代码 + rodata ≤ 2 MB，
   `.ark_buf` 落在两个布局各自的区间内）；
7. **全量门禁**：`make test` EXIT=0（含本切片新增的 `make test-vreg`）。

## 6 否证条件（写死，触发即收档）

- **F1**：S6a 落地后总下降 **< 5%** ⇒ 收档（这一条比 0.5% 严，因为换模型本身有风险成本）；
- **F2**：任一 TU 变大 ⇒ 收档；
- **F3**：`arm_exec` 出现一个无法归因到「未实现的形状」的 failure ⇒ 收档（**宁可报错，不给错答案**）；
- **F4**：S6a 必须用超过 `r0`–`r3` 四个寄存器、或必须 spill 才能过 5% ⇒ 收档，
  退回文本层继续找（那说明块内本来就没有这么多可用寄存器）。

## 7 裁切

- `ARKCC_FEATURE_VREG`：`ARKCC_PROFILE_STM32_MIN` ⇒ 0，宿主与交叉构建 ⇒ 1，默认**关**；
- 关闭时：不运行的代码，且不改变任何既有产物（OFF IS OFF 是逐字节保证）；
- 主体是新的发射器而不是新表，因此板上裁掉它只省代码体积，不影响其它 pass。

## 8 风险与回滚

| 风险 | 处理 |
| --- | --- |
| S6a 的正确性（最难的是「栈语义 ↔ 寄存器语义」的等价） | 每个函数在 S6a 前后做一次 `memcmp` 级等价自检不成立（文本本来就该变），所以判据只能靠**执行级**：95 TU 语料 + `arm_exec` 全量 + 逐函数差分探针 |
| 与 `ark_regalloc_function()` 抢保存寄存器块 | 写死「`PUSH` 加宽与偏移平移只有一个所有者」（`docs/OPERAND_ALLOC.md` §4）；做不到则 S6c 降级为不做 |
| 长函数（`HAL_RCC_OscConfig` 3,156 条）区间爆炸 | 线性扫描按区间端点排序，O(n log n)；区间上限触发整函数弃权（回到 vstack 路径） |
| 调试可读性 | `-g` 下需要保留变量位置信息；S6 未做之前不接受「调试信息丢失」 |

回滚方式：单个旗标默认关；`--pipeline=lite` 可跳过；不删任何既有代码路径。

## 10 实施前的否定性度量（2026-11-23，先量再动手）

本节是在写任何 S6 代码之前，对「文本层还有没有钱可挖」做的四次实测。四条全部为负或可忽略，且第四条给出了收益形式的上界——它直接决定了 S6a 的**实施形式**（见 §10.5）。所有数字均在 95 TU 语料、`-O2` 十六开关口径下取得；`base` 在同一次运行内自检必须等于 **18,151**。

### 10.1 `-fopt-regalloc` 的现役默认档是空转

| 臂 | 总指令 | 相对 base |
| --- | --- | --- |
| base（十六开关） | 18,151 | — |
| `+ -fopt-regalloc` | 18,151 | **0，95/95 逐字节相同** |
| `+ -fopt-regalloc-near` | 18,174 | +23（+0.13%，3 TU 变小 2 TU 变大） |

默认档零效果**不是 bug**，是两重设计边界同时命中：

1. 默认档只收「宽访存」槽（偏移 >124 或非 4 字节对齐才值得加宽 `PUSH`），而 HAL 的局部变量几乎全落在 `0..124` 且 4 字节对齐 ⇒ `saves = 0`，一个槽都不选；
2. `ra_classify()` 只认 `LDR r0,[r6,#n]` / `STR r0,[r6,#n]` 这一种形状，而 `-fopt-vstack` 已经把大部分访存改成经 `r5`/`r7` 的影子栈形状 ⇒ 这些行被当成 taint 丢弃。

结论：现役文本层保存寄存器（slot caching）即便打开也拿不到收益；`-near` 的 +23 是噪声量级。

### 10.2 槽缓存只会把「访存」换成「MOV」，指令数不降反升

一个 `HAL_GPIO_ReadPin` 实例（`-fopt-regalloc-near`）：

```asm
STR r0, [r6, #16]     ; 原：把返回值存到槽
...
LDR r0, [r6, #16]     ; 原：从槽取回
```

被改写成

```asm
MOV r8, #1            ; 槽里存的常量被直接 MOV 进缓存寄存器
MOV r0, #1            ; 还多出一条冗余的立即数装载
...
MOV r0, r8            ; 取下时改成寄存器 MOV
```

两件事同时发生：**条数没少**（`STR`→`MOV`、`LDR`→`MOV` 一一对应），而且 `MOV r5, r8`（高寄存器之间）是 **32 位编码**，比原来的 `LDR r5, [r6, #16]`（16 位）**更宽**。所以「缓存 + MOV 替换」这条形式在字节上必然亏，不能作为 S6a 的落点。

### 10.3 `-fopt-pair` 与 `--reg-top` 都被既有开关支配

| 臂 | 总指令 | 相对 base |
| --- | --- | --- |
| `+ -fopt-pair` | 18,145 | **−6（−0.03%），5 TU 变小 0 变大** |
| `--reg-top`（去掉 imm / cbranch 的比较公平臂） | 24,812 | **+6,661（+36.7%）** |
| `--reg-top + -fopt-pair` | 24,800 | 同一量级，pair 只省 12 |

`-fopt-pair` 在完整十六开关下只剩 6 条，说明相邻 `MOV` 合并这件事已经被 `-fopt-imm` / `-fopt-cbranch` 吃干净；而把这两个开关摘掉后 pair 也救不回来（仍 24,8xx）。⇒ pair 收档，不作为 S6 的输入。

### 10.4 文本层收益的上界（决定性）

在 18,151 条里，最简单的帧访存 `LDR/STR rN,[r6,#n]` 共 **1,845** 条（LDR 1,306 / STR 539）：

- **99.8%（1,842 条）** 落在「从未被取址」的槽上（函数内没有 `ADD/SUB rX, r6, #n` 指向它们）；
- 若每函数把访问次数最高的 4 个槽常驻 `r8-r11`，可消除的**绝对上界**是 **1,714 条 = 9.4%**；
- 「存后同寄存器重载」（`LDR rX,[slot]` 紧接同槽同寄存器的 `STR`）只有 **80 条（0.44%）**；
- 「语句间 STR→LDR 前送」可折叠的对只有 **52 对 → 104 条（0.6%）**。

即使把这 1,714 条全拿到，也只到 16,437（对 armcc 仍 2.9×）。⇒ **文本层路线到此为止**，与 §2 的结论一致。

### 10.5 由 10.2 与 10.4 推出的实施形式修订（门禁不变）

§4 原本把 S6a 写成「缓存到 `r8-r11` + 把访问替换成 MOV」。10.2 证明「替换成 MOV」在字节上必亏，10.4 证明唯一有价值的收益是「让访问整条消失」。因此 **S6a 的实施形式修订为**：

> **槽缓存 + 改名消除（rename elision）**：命中的 `LDR rX,[slot]` 不是换成 `MOV rX, rCache`，而是**把消耗这个值的直线段内的目的寄存器改名为 `rCache` 并删掉该 `LDR`**；对应的 `STR rCache,[slot]` 一侧则由「把生产者的目的寄存器直接改成 `rCache`、删掉 `STR`」完成。段边界复用 `-fopt-coalesce` 的 `lv_same` 回放校验；但因 `rCache` 是 callee-saved，`BL` **不再是屏障**（这正是它比 coalesce 能多做的原因）。

这与 §3 的「vreg + 线性扫描」是同一目标（值住在哪个寄存器由模型决定，而不是由文本模式猜），**§5 的 7 条冻结门禁与 §6 的 F1-F4 一字不改**；只把「怎么写」从替换改成消除，把预期收益锚定到 10.4 的 9.4% 上界内（S6a 的 −8% ≥1,450 条仍成立，且留出 264 条余量给实现损耗）。

## 11 落地实测（2026-11-23，S6a 实现完成）

实现形式按 §10.5 落地：旗标 `-fopt-vreg`，**默认关**；裁剪构建（`-DARKCC_FEATURE_OPT_VREG=0`）按名拒绝（C3900U）而不是接受后什么都不做。

### 11.1 与既有 pass 的协作方式（为什么必须后跑）

`-fopt-constcache` 长在 `ark_regalloc_function()` 内部，和 vreg 抢同一个 `r8-r11` 池与同一对 `PUSH/POP`。因此 vreg **不是** override regalloc，而是排在它后面：

1. `regalloc`（含 constcache）先把槽缓存到 `r8-r11`、加宽帧；
2. `vreg` 再从**文本**里读出 `PUSH` 列表、已占用寄存器位图与 `base = local_eff + 4 * saved_words`，只在剩下的寄存器里工作，加宽时把 `>= base` 的偏移整体平移。

首版让 vreg 排在 regalloc 之前，95 个 TU 合计 **18,151 → 18,310（+159）**：`MOV r5, r8` 与 `MOVW+MOVT` 的收益全被吃掉。改成协作后是 **−415**。

### 11.2 三条实现口径

- **装载目的寄存器是 r0–r7，不是固定 r0**：`-fopt-vstack` 把槽流量搬到 `r5/r7`（`LDR r5,[r6,#n]`），只认 `LDR r0` 会让整条路线在 vstack 下失效（实测只拿到 −270）；改名/删除都按「装载实际写的那个寄存器」参数化。
- **每槽要求 `elid >= 2`**：只按指令数记账（`PUSH/POP` 加宽不增指令但每寄存器多 4 B 栈流量），省 1 条不值得多压一个字。
- **`saved_words = PUSH 列表寄存器数 + 1`**（`lr` 占一字），`base = local_eff + 4 * saved_words`；加宽后若 `(saved_words + nregs)` 为奇数，从空闲池补一个寄存器把帧拉回 8 字节对齐。

### 11.3 实测数字（95 个 TU，Cortex-M4，十六开关 + `-fopt-coalesce`）

| 口径 | 指令数 | 相对基线 |
|---|---|---|
| 基线（无 `-fopt-vreg`） | 18,151 | — |
| `-fopt-vreg` | **17,736** | **−415（−2.29%）** |

### 11.4 门禁（`tests/run_vreg_tests.py`，全绿）

1. **OFF IS OFF**：默认 `-O2` 与 `-O2 -fno-opt-vreg` 逐字节相同（1,218/1,218 字节，含镜像）。
2. **IT PAYS**：四个重载夹具（`chain/loop/many/call`，都是「结构体指针 + 远偏移」形态，产生 `LDR rX,[r6,#n]` 紧跟消费指令）指令数严格下降；**任何夹具都不增**——这条 pass 没有「加一条指令」的形态。
3. **帧是同一个帧**：被提升函数的 `PUSH/POP` 加同一批寄存器（记为 `added`），`>= base` 的调用方/va 区偏移按 `4 × len(added)` 平移，加宽区内不留偏移。

### 11.5 附带发现（本轮已修）

`-fopt-vstack` 在**调用实参多于 4 个**且函数体用到第 5/6 个实参时错编译：vstack 为第三槽征用 `r4` 使帧加宽 4 字节，但前端的「实参拷贝」`LDR r0,[r6,#n]` 偏移仍按 4 个保存字计算，读到低 4/8 字节的另一个位置。

复现：`int h2(int a,int b,int c,int d,int e,struct VgS *p){return e + p->a;}`，`-fopt-vstack` 下返回值是 `0x30B0xxxx` 而非 6；不带该旗标与只开 `-fopt-regalloc -fopt-constcache` 都正确（5 个实参正确、6 个才错，纯整数 6 实参不受影响，需要一次访存）。

该开关默认关（0.9.1-wip），因此不影响 `-O2` 现状。修法：vstack 加宽帧后调用新增的 `vs_shift_r6()`，把 `>= frame` 的 `[r6, #n]` 全部平移 **+8**（`PUSH` 多压一个字 **加上** 帧多 4 字节，调用方实参相对 `r6` 一共上移两个字；只移 +4 会读到中间那块保存区，实测立即 `UC_ERR_READ_UNMAPPED`）。修后 `h2` 在 `-fopt-vstack` 下返回 6，`vg3`（`p->a + p->d + a + b + c + d + e`）返回 56；`run_vstack_tests.py` 与 `run_vreg_tests.py` 均全绿，95 TU 合计仍为 18,151（只改立即数，不改指令数）。

## 12 落地实测（2026-11-23，S6b 实现完成：块内全量重命名）

S6a 只吃「紧跟在消费者之前的那一条 load」。S6b 把区域放宽到**基本块内**：一条被提升槽的 load 被删掉之后，同一个基本块里**所有**读它目的寄存器的行都改读缓存寄存器，直到下列任一事件结束区域，只有这四种：① 屏障行（标签、分支/跳转、`BL`/`BLX`、PUSH/POP 与帧建立）；② 帧建立行本身；③ 另一条把这个目的寄存器当写目标的帧装载（`LDR rD, [r6,#m]`，此后 `rD` 里已不是缓存寄存器那个值）；④ 任何一行**只写不读** `rD`。除此之外都只是改名后继续——包括别的槽的访存（只要不落在 `rD` 上）、以及源操作数是 `rD` 的 store（那条 store 也改名，否则会把旧值写回内存）。读改写（`ADD r0, r1` 当 `r0` 就是目的寄存器）同样改名并保留：缓存寄存器带着更新后的值沿同一条路径往下走，因此不需要在区域中途把值写回。这一节只登记实测与实现，§5 的冻结门禁与 §6 的否证线一字未改。

### 12.1 与 S6a 的差别（三条，以及和 §4 计划表的出入）

先说清一处出入：§4 把 S6b 写成「跨块：线性扫描 + 区间合并」。实际落地时先做的是**块内全量重命名**——区域边界仍然是块内单路径（遇分支/标签即结束），没有跨块活跃性、也没有区间合并。S6a 的 −2.29% 与 F1（<5% 即收档）之间还差得远，而块内重命名不需要 CFG 就能吃掉大部分读点，所以先把它做成独立一片并单独收档；「跨块线性扫描 + 区间合并」整体顺延为 **S6b-2**，仍受同一条 F1 约束。


1. **区域：1 行 → 整个基本块**。同一槽的多条 load 现在各自能吃掉后面一段读点，命中数从「紧跟消费者」放大到「块内全部读点」。
2. **一行可以带多个改名**：块宽之后同一行可能同时读两个已提升槽（如 `ADD r0, r3, r4`），所以改名从「单对 `(from,to)`」改成**每行最多 4 对的映射表**（`VG_MAX_MAP 4`），并按顺序叠加。
3. **帧对齐从「补一个字」改成「补一个寄存器」**：`PUSH` 之前帧已 8 对齐，新增 `nregs` 个寄存器后仍对齐 ⇔ **`nregs` 为偶数**（与 `saved_words` 奇偶无关）。奇数时从空闲池再拿一个 r8–r11 补上——`PUSH` 里任何一个 r8–r11 名字都是 32 位，补一个不多花指令；池里没有富余就整函数放弃。

### 12.4 四个真缺陷（都是在槽被提升到 `r8-r11` 之后才现形的）

这四个都不是新代码的笔误，而是**既有代码在只有 r0–r7 时才恰好正确的假设**。`-fopt-vreg` 第一次把局部量放进 r8–r11、第一次把两操作数移位真实地喂进汇编器，四处假设同时崩。

**12.4.1 内建汇编器对高寄存器静默截断（CMP / 立即数 CMP / NEG / MUL）**

| 源文本 | 修前编码 | 后果 |
|---|---|---|
| `CMP r9, r7` | `cmp r1, r15` | 比错两个寄存器，条件码全错 |
| `CMP r9, #4` | `cmp r1, #4` | T1 16 位 `CMP Rn,#imm8` 的 Rn 只有 3 位，代码不看 `rn` 就硬塞 |
| `NEG r9, r7` | `rsbs r1, r7, #0` | 目标被截成 r1 |
| `MUL r9, r8, r7` | 硬报错并停 | T2 32 位本就支持三个互不相同的寄存器 |

修法不是「加个判断拒绝」，而是把 32 位形式补齐：`CMP` 走 `0xEBB0|Rn` + `0x0F00|Rm`；`CMP Rn,#imm` 走 `0xF1B0|i<<10|Rn` + `imm3<<12|0x0F00|imm8`；`NEG`=`RSB Rd,Rm,#0` 走 `0xF1C0|Rm` + `Rd<<8`；`MUL` 走 `0xFB00|Rn` + `0xF000|Rd<<8|Rm`。同时**把 pass 1 的字节宽度判据同步改对**——这一层比编码本身更要紧：`MUL` 的 pass 1 原先把第三寄存器 `rn1` 直接 `(void)` 掉，于是 `MUL r1,r2,r3` 按 2 字节布局、pass 2 写 4 字节（或反之），标签全体漂移。**两遍宽度必须由同一条判据推出**。

顺带确证了一个先前被我修错一次的字段：T2 16 位 `CMP Rn,Rm`（`0100 0101 0 Rm Rn`）里 **Rm 是 bits[6:3] 的完整四位**、**Rn 只有三位**、bit7 恒 0。gas 实测 `CMP r1, r9` = `0x4549`。第一次修复把 bit3 当成 Rn 的 N 位，编码出来还是错的；现在 gas / capstone / unicorn 三方一致。

**12.4.2 两操作数移位的操作数角色反了（本轮最严重）**

Thumb 两操作数 `LSL Rd, Rs` 的语义是 **`Rd = Rd << Rs`**——被移位的值是**目的寄存器自己**，第二操作数是移位量。原实现写成「被移位值 = 第二操作数」，于是 `LSL r0, r1` 被汇编成 `lsls r0, r0, r0`。

暴露路径：`run_coalesce_tests.py` 的 `merge` / `selfsrc` 夹具里 `alone` 臂（只开 `-fopt-coalesce`，没有强度削减把 `<<3` 折成立即数）返回 2070 / 5，期望 86 / 35。用 unicorn 追 SRAM 写入定位到 `cs_c = 0x800`（`8 << 8`，应为 `8 << 3`）。

修法是把三种操作数形态分开：

```c
if (rs >= 0)     { rn_src = rm; rs_amt = rs; }   /* 三操作数 Rd, Rn, Rs */
else if (is_imm) { rn_src = rm; rs_amt = rd; }   /* 立即数   Rd, Rn, #imm  */
else             { rn_src = rd; rs_amt = rm; }   /* 两操作数 Rd, Rs -> Rd = Rd shift Rs */
```

这类缺陷的可怕之处在于**它一直存在**：只要没有真实的两操作数移位流到汇编器，它就一直不发作。`-fopt-strength` 把 `x << 3` 折成立即数，恰好把它盖住；夹具里故意保留的那一臂才把它顶出来。

**12.4.3 `vg_reads_reg` 分不清「只写」与「读改写」**

块宽之后，区域边界要靠「这一行是否写/读目的寄存器」来判断。首版把**第一操作数一律当写目标**：`ADD r0, r1` 是两操作数形式（`r0 = r0 + r1`），它**读** r0，首版判成只写 ⇒ 区域提前结束，该行不参与改名 ⇒ 这一行读的仍是低位寄存器里的旧值。方向反过来也危险：把读改写成只写会让缓存寄存器与低位寄存器分叉。

定稿规则：**第一操作数之外的每个操作数都算读**；第一操作数在**两操作数数据运算形式**（`ADD/SUB/AND/ORR/EOR/ADC/SBC/RSB/RSC/MUL/MLA/BIC/ORN/LSL/LSR/ASR/ROR/RRX/MVN/NEG`）下也算读，其余（`LDR`/`MOV`/`MOVW`/`MOVT`/`LDRB`…）只算写。宁可多判一次「读」（多一次改名），因为改名的代价只是把同一个值再搬到缓存寄存器，漏判的代价是错答案。

**12.4.4 原地重命名会覆盖仍在读的文本**

`r8` 比 `r3` 长一个字符。第一版在同一个缓冲区里把 `r3` 就地替换成 `r8`，第二次改名再从那片已经被拉长/改写的文本里读 ⇒ 越界或错位。修法是**双缓冲 ping-pong**：`line → rl → rl2 → …`，读一个缓冲、写另一个，最后把 `res` 指针指向最后写成的那个。
