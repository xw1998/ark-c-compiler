## 2 为什么不能再用文本层

三条已经做过的尝试，都是同一堵墙：

1. `-fopt-slotreg`（P17）：不带安全闸能删 −1.82%，但 5 个 `arm_exec` failure
   （`memcpy` 在内部间接读，文本层看不见）。带闸只剩 −0.34%，**收档**。
2. `-fopt-constcache`（P18/S3a）与 **S3b**：S3b 想省「跨调用活着的值」，
   实测 95 个 TU 里真实机会只有 **5 对 / 0.11%**，**收档**。
3. `-fopt-coalesce`（L5）：81/95 个 TU 逐字节不变，−1.93%；剩下的拷贝一律卡在
   「段内有 `BL`」或「源在段内被写」。

结论：**文本上看不见「这个值此刻在哪个寄存器里」**，所以每一条规则都必须先把
「看不见的读写」当成危险来防——防到安全时收益就没了。要有下一层收益，必须让
「值住在哪个寄存器」成为编译器里的**一等对象**，而不是事后猜。

## 3 目标模型

现在的模型（`docs/RA_VSTACK.md` §1）：IR 是栈机，发射期每个中间值 `PUSH`/`POP`，
`-fopt-vstack` 事后把相邻往返折成 r0/r5/r7 的搬运，其余落回帧。

目标模型：

```
irgen（不变） → IR（不变） → 新的 IR→文本发射器（S6） → 汇编（不变）
                                  ↑
                      虚拟寄存器 + 线性扫描 + spill
```

- **虚拟寄存器**：`IR_PUSH` 与产生值的指令在 S6 里得到一个 `vreg`，不再隐含 r0；
  栈语义由 `vreg` 编号的活跃区间表达，不再有 `PUSH`/`POP` 的机器栈含义。
- **寄存器池**：
  - caller-saved `r0`–`r3`：块内、且活跃区间不跨 `BL` 的值；
  - callee-saved `r8`–`r11`：活跃区间跨 `BL` 的值，代价是每函数一次 `PUSH` 加宽
    （与 `ark_regalloc_function()` 共用同一段保存块，**只允许一个所有者**，
    这条约束在 `docs/OPERAND_ALLOC.md` §4 已经写死）。
  - `r6` 仍是帧基址（不把它交出去：取消帧指针实测只值 0.2%）。
- **活跃区间**：按 IR 线性序 + 基本块（`src/mir.c` 已有 CFG）计算，块边界按
  succ 合并；`RETURN` / `BL` / 间接调用是切分点。
- **spill**：只在 S6c 引入；溢出到帧槽，槽位由 `alloc_local()` 同一套分配器给。
- **与 `-fopt-vstack` 的关系：二选一**（`docs/OPTIMIZER_PLAN.md` P12 S5 的原判）。
  S6 一旦并线，`-fopt-vstack` 的文本重建在同一函数上不再运行；默认保留谁由语料实测决定，
  另一条留作回退开关。

## 5 冻结门禁（实现前不改）

1. **OFF IS OFF**：`-O2` 与 `-O2 -fno-opt-vreg` 逐字节相同（95/95 TU）；
2. **只减不增**：任一 TU 指令数变大即红，不做「平均更好」的解释；
3. **默认关**：`enable_opt_vreg = 0`，INI/CLI 双向可开关；
4. **执行级同值**：`tests/arm_exec/run_arm_exec.py --extra=-fopt-vreg` 全量 0 failure，
   且每条断言仍是「程序外算出的常量」，不允许改成自证；
5. **裁剪拒绝**：`-DARKCC_FEATURE_VREG=0` 的构建以
   `Fatal error: C3900U: -fopt-vreg is not compiled into this build` 拒绝并返回 1，
   不带旗标仍能编译；
6. **板端体积**：`tools/stm32_build_check.py --layout both` 仍全 PASS（代码 + rodata ≤ 2 MB，
   `.ark_buf` 落在两个布局各自的区间内）；
7. **全量门禁**：`make test` EXIT=0（含本切片新增的 `make test-vreg`）。

- **F1**：S6a 落地后总下降 **< 5%** ⇒ 收档（这一条比 0.5% 严，因为换模型本身有风险成本）；

## 7 裁切

- `ARKCC_FEATURE_VREG`：`ARKCC_PROFILE_STM32_MIN` ⇒ 0，宿主与交叉构建 ⇒ 1，默认**关**；
- 关闭时：不运行的代码，且不改变任何既有产物（OFF IS OFF 是逐字节保证）；

## 8 风险与回滚

| 风险 | 处理 |
| --- | --- |
| S6a 的正确性（最难的是「栈语义 ↔ 寄存器语义」的等价） | 每个函数在 S6a 前后做一次 `memcmp` 级等价自检不成立（文本本来就该变），所以判据只能靠**执行级**：95 TU 语料 + `arm_exec` 全量 + 逐函数差分探针 |
| 与 `ark_regalloc_function()` 抢保存寄存器块 | 写死「`PUSH` 加宽与偏移平移只有一个所有者」（`docs/OPERAND_ALLOC.md` §4）；做不到则 S6c 降级为不做 |
| 长函数（`HAL_RCC_OscConfig` 3,156 条）区间爆炸 | 线性扫描按区间端点排序，O(n log n)；区间上限触发整函数弃权（回到 vstack 路径） |
| 调试可读性 | `-g` 下需要保留变量位置信息；S6 未做之前不接受「调试信息丢失」 |

回滚方式：单个旗标默认关；`--pipeline=lite` 可跳过；不删任何既有代码路径。

## 10 实施前的否定性度量（2026-11-23，先量再动手）

本节是在写任何 S6 代码之前，对「文本层还有没有钱可挖」做的四次实测。四条全部为负或可忽略，且第四条给出了收益形式的上界——它直接决定了 S6a 的**实施形式**（见 §10.5）。所有数字均在 95 TU 语料、`-O2` 十六开关口径下取得；`base` 在同一次运行内自检必须等于 **18,151**。

### 10.1 `-fopt-regalloc` 的现役默认档是空转

| 臂 | 总指令 | 相对 base |
| --- | --- | --- |
| base（十六开关） | 18,151 | — |
| `+ -fopt-regalloc` | 18,151 | **0，95/95 逐字节相同** |
| `+ -fopt-regalloc-near` | 18,174 | +23（+0.13%，3 TU 变小 2 TU 变大） |

默认档零效果**不是 bug**，是两重设计边界同时命中：

1. 默认档只收「宽访存」槽（偏移 >124 或非 4 字节对齐才值得加宽 `PUSH`），而 HAL 的局部变量几乎全落在 `0..124` 且 4 字节对齐 ⇒ `saves = 0`，一个槽都不选；
2. `ra_classify()` 只认 `LDR r0,[r6,#n]` / `STR r0,[r6,#n]` 这一种形状，而 `-fopt-vstack` 已经把大部分访存改成经 `r5`/`r7` 的影子栈形状 ⇒ 这些行被当成 taint 丢弃。

结论：现役文本层保存寄存器（slot caching）即便打开也拿不到收益；`-near` 的 +23 是噪声量级。

### 10.2 槽缓存只会把「访存」换成「MOV」，指令数不降反升

一个 `HAL_GPIO_ReadPin` 实例（`-fopt-regalloc-near`）：

```asm
STR r0, [r6, #16]     ; 原：把返回值存到槽
...
LDR r0, [r6, #16]     ; 原：从槽取回
```

被改写成

```asm
MOV r8, #1            ; 槽里存的常量被直接 MOV 进缓存寄存器
MOV r0, #1            ; 还多出一条冗余的立即数装载
...
MOV r0, r8            ; 取下时改成寄存器 MOV
```

两件事同时发生：**条数没少**（`STR`→`MOV`、`LDR`→`MOV` 一一对应），而且 `MOV r5, r8`（高寄存器之间）是 **32 位编码**，比原来的 `LDR r5, [r6, #16]`（16 位）**更宽**。所以「缓存 + MOV 替换」这条形式在字节上必然亏，不能作为 S6a 的落点。

### 10.3 `-fopt-pair` 与 `--reg-top` 都被既有开关支配

| 臂 | 总指令 | 相对 base |
| --- | --- | --- |
| `+ -fopt-pair` | 18,145 | **−6（−0.03%），5 TU 变小 0 变大** |
| `--reg-top`（去掉 imm / cbranch 的比较公平臂） | 24,812 | **+6,661（+36.7%）** |
| `--reg-top + -fopt-pair` | 24,800 | 同一量级，pair 只省 12 |

`-fopt-pair` 在完整十六开关下只剩 6 条，说明相邻 `MOV` 合并这件事已经被 `-fopt-imm` / `-fopt-cbranch` 吃干净；而把这两个开关摘掉后 pair 也救不回来（仍 24,8xx）。⇒ pair 收档，不作为 S6 的输入。

**2026-11-24 补测（十九开关口径，基线 12,304）**：`--reg-top` 在十九开关基线上是
**18,997 = +6,693（+54.4%）**，比十六开关的 +36.7% **更差**。这说明 `--reg-top` 的收益被
越多既有开关吃掉越多、它自己又必付 `MOV`/加宽代价 ⇒ **该基座不可复用**，任何「在 `--reg-top`
上接 S6」的想法都不成立。

### 10.4 文本层收益的上界（决定性）

在 18,151 条里，最简单的帧访存 `LDR/STR rN,[r6,#n]` 共 **1,845** 条（LDR 1,306 / STR 539）：

- **99.8%（1,842 条）** 落在「从未被取址」的槽上（函数内没有 `ADD/SUB rX, r6, #n` 指向它们）；
- 若每函数把访问次数最高的 4 个槽常驻 `r8-r11`，可消除的**绝对上界**是 **1,714 条 = 9.4%**；
- 「存后同寄存器重载」（`LDR rX,[slot]` 紧接同槽同寄存器的 `STR`）只有 **80 条（0.44%）**；
- 「语句间 STR→LDR 前送」可折叠的对只有 **52 对 → 104 条（0.6%）**。

即使把这 1,714 条全拿到，也只到 16,437（对 armcc 仍 2.9×）。⇒ **文本层路线到此为止**，与 §2 的结论一致。

### 10.5 由 10.2 与 10.4 推出的实施形式修订（门禁不变）

§4 原本把 S6a 写成「缓存到 `r8-r11` + 把访问替换成 MOV」。10.2 证明「替换成 MOV」在字节上必亏，10.4 证明唯一有价值的收益是「让访问整条消失」。因此 **S6a 的实施形式修订为**：

> **槽缓存 + 改名消除（rename elision）**：命中的 `LDR rX,[slot]` 不是换成 `MOV rX, rCache`，而是**把消耗这个值的直线段内的目的寄存器改名为 `rCache` 并删掉该 `LDR`**；对应的 `STR rCache,[slot]` 一侧则由「把生产者的目的寄存器直接改成 `rCache`、删掉 `STR`」完成。段边界复用 `-fopt-coalesce` 的 `lv_same` 回放校验；但因 `rCache` 是 callee-saved，`BL` **不再是屏障**（这正是它比 coalesce 能多做的原因）。

这与 §3 的「vreg + 线性扫描」是同一目标（值住在哪个寄存器由模型决定，而不是由文本模式猜），**§5 的 7 条冻结门禁与 §6 的 F1-F4 一字不改**；只把「怎么写」从替换改成消除，把预期收益锚定到 10.4 的 9.4% 上界内（S6a 的 −8% ≥1,450 条仍成立，且留出 264 条余量给实现损耗）。

## 11 落地实测（2026-11-23，S6a 实现完成）

实现形式按 §10.5 落地：旗标 `-fopt-vreg`，**默认关**；裁剪构建（`-DARKCC_FEATURE_OPT_VREG=0`）按名拒绝（C3900U）而不是接受后什么都不做。

### 11.1 与既有 pass 的协作方式（为什么必须后跑）

`-fopt-constcache` 长在 `ark_regalloc_function()` 内部，和 vreg 抢同一个 `r8-r11` 池与同一对 `PUSH/POP`。因此 vreg **不是** override regalloc，而是排在它后面：

1. `regalloc`（含 constcache）先把槽缓存到 `r8-r11`、加宽帧；
2. `vreg` 再从**文本**里读出 `PUSH` 列表、已占用寄存器位图与 `base = local_eff + 4 * saved_words`，只在剩下的寄存器里工作，加宽时把 `>= base` 的偏移整体平移。

首版让 vreg 排在 regalloc 之前，95 个 TU 合计 **18,151 → 18,310（+159）**：`MOV r5, r8` 与 `MOVW+MOVT` 的收益全被吃掉。改成协作后是 **−415**。

### 11.2 三条实现口径

- **装载目的寄存器是 r0–r7，不是固定 r0**：`-fopt-vstack` 把槽流量搬到 `r5/r7`（`LDR r5,[r6,#n]`），只认 `LDR r0` 会让整条路线在 vstack 下失效（实测只拿到 −270）；改名/删除都按「装载实际写的那个寄存器」参数化。
- **每槽要求 `elid >= 2`**：只按指令数记账（`PUSH/POP` 加宽不增指令但每寄存器多 4 B 栈流量），省 1 条不值得多压一个字。
- **`saved_words = PUSH 列表寄存器数 + 1`**（`lr` 占一字），`base = local_eff + 4 * saved_words`；加宽后若 `(saved_words + nregs)` 为奇数，从空闲池补一个寄存器把帧拉回 8 字节对齐。

## 12 落地实测（2026-11-23，S6b 实现完成：块内全量重命名）

S6a 只吃「紧跟在消费者之前的那一条 load」。S6b 把区域放宽到**基本块内**：一条被提升槽的 load 被删掉之后，同一个基本块里**所有**读它目的寄存器的行都改读缓存寄存器，直到下列任一事件结束区域，只有这四种：① 屏障行（标签、分支/跳转、`BL`/`BLX`、PUSH/POP 与帧建立）；② 帧建立行本身；③ 另一条把这个目的寄存器当写目标的帧装载（`LDR rD, [r6,#m]`，此后 `rD` 里已不是缓存寄存器那个值）；④ 任何一行**只写不读** `rD`。除此之外都只是改名后继续——包括别的槽的访存（只要不落在 `rD` 上）、以及源操作数是 `rD` 的 store（那条 store 也改名，否则会把旧值写回内存）。读改写（`ADD r0, r1` 当 `r0` 就是目的寄存器）同样改名并保留：缓存寄存器带着更新后的值沿同一条路径往下走，因此不需要在区域中途把值写回。这一节只登记实测与实现，§5 的冻结门禁与 §6 的否证线一字未改。

### 12.1 与 S6a 的差别（三条，以及和 §4 计划表的出入）

先说清一处出入：§4 把 S6b 写成「跨块：线性扫描 + 区间合并」。实际落地时先做的是**块内全量重命名**——区域边界仍然是块内单路径（遇分支/标签即结束），没有跨块活跃性、也没有区间合并。S6a 的 −2.29% 与 F1（<5% 即收档）之间还差得远，而块内重命名不需要 CFG 就能吃掉大部分读点，所以先把它做成独立一片并单独收档；「跨块线性扫描 + 区间合并」整体顺延为 **S6b-2**，仍受同一条 F1 约束。


1. **区域：1 行 → 整个基本块**。同一槽的多条 load 现在各自能吃掉后面一段读点，命中数从「紧跟消费者」放大到「块内全部读点」。
2. **一行可以带多个改名**：块宽之后同一行可能同时读两个已提升槽（如 `ADD r0, r3, r4`），所以改名从「单对 `(from,to)`」改成**每行最多 4 对的映射表**（`VG_MAX_MAP 4`），并按顺序叠加。
3. **帧对齐从「补一个字」改成「补一个寄存器」**：`PUSH` 之前帧已 8 对齐，新增 `nregs` 个寄存器后仍对齐 ⇔ **`nregs` 为偶数**（与 `saved_words` 奇偶无关）。奇数时从空闲池再拿一个 r8–r11 补上——`PUSH` 里任何一个 r8–r11 名字都是 32 位，补一个不多花指令；池里没有富余就整函数放弃。

### 12.4 四个真缺陷（都是在槽被提升到 `r8-r11` 之后才现形的）

这四个都不是新代码的笔误，而是**既有代码在只有 r0–r7 时才恰好正确的假设**。`-fopt-vreg` 第一次把局部量放进 r8–r11、第一次把两操作数移位真实地喂进汇编器，四处假设同时崩。

**12.4.1 内建汇编器对高寄存器静默截断（CMP / 立即数 CMP / NEG / MUL）**

| 源文本 | 修前编码 | 后果 |
|---|---|---|
| `CMP r9, r7` | `cmp r1, r15` | 比错两个寄存器，条件码全错 |
| `CMP r9, #4` | `cmp r1, #4` | T1 16 位 `CMP Rn,#imm8` 的 Rn 只有 3 位，代码不看 `rn` 就硬塞 |
| `NEG r9, r7` | `rsbs r1, r7, #0` | 目标被截成 r1 |
| `MUL r9, r8, r7` | 硬报错并停 | T2 32 位本就支持三个互不相同的寄存器 |

修法不是「加个判断拒绝」，而是把 32 位形式补齐：`CMP` 走 `0xEBB0|Rn` + `0x0F00|Rm`；`CMP Rn,#imm` 走 `0xF1B0|i<<10|Rn` + `imm3<<12|0x0F00|imm8`；`NEG`=`RSB Rd,Rm,#0` 走 `0xF1C0|Rm` + `Rd<<8`；`MUL` 走 `0xFB00|Rn` + `0xF000|Rd<<8|Rm`。同时**把 pass 1 的字节宽度判据同步改对**——这一层比编码本身更要紧：`MUL` 的 pass 1 原先把第三寄存器 `rn1` 直接 `(void)` 掉，于是 `MUL r1,r2,r3` 按 2 字节布局、pass 2 写 4 字节（或反之），标签全体漂移。**两遍宽度必须由同一条判据推出**。

顺带确证了一个先前被我修错一次的字段：T2 16 位 `CMP Rn,Rm`（`0100 0101 0 Rm Rn`）里 **Rm 是 bits[6:3] 的完整四位**、**Rn 只有三位**、bit7 恒 0。gas 实测 `CMP r1, r9` = `0x4549`。第一次修复把 bit3 当成 Rn 的 N 位，编码出来还是错的；现在 gas / capstone / unicorn 三方一致。

**12.4.2 两操作数移位的操作数角色反了（本轮最严重）**

Thumb 两操作数 `LSL Rd, Rs` 的语义是 **`Rd = Rd << Rs`**——被移位的值是**目的寄存器自己**，第二操作数是移位量。原实现写成「被移位值 = 第二操作数」，于是 `LSL r0, r1` 被汇编成 `lsls r0, r0, r0`。

暴露路径：`run_coalesce_tests.py` 的 `merge` / `selfsrc` 夹具里 `alone` 臂（只开 `-fopt-coalesce`，没有强度削减把 `<<3` 折成立即数）返回 2070 / 5，期望 86 / 35。用 unicorn 追 SRAM 写入定位到 `cs_c = 0x800`（`8 << 8`，应为 `8 << 3`）。

修法是把三种操作数形态分开：

```c
if (rs >= 0)     { rn_src = rm; rs_amt = rs; }   /* 三操作数 Rd, Rn, Rs */
else if (is_imm) { rn_src = rm; rs_amt = rd; }   /* 立即数   Rd, Rn, #imm  */
else             { rn_src = rd; rs_amt = rm; }   /* 两操作数 Rd, Rs -> Rd = Rd shift Rs */
```

这类缺陷的可怕之处在于**它一直存在**：只要没有真实的两操作数移位流到汇编器，它就一直不发作。`-fopt-strength` 把 `x << 3` 折成立即数，恰好把它盖住；夹具里故意保留的那一臂才把它顶出来。

**12.4.3 `vg_reads_reg` 分不清「只写」与「读改写」**

块宽之后，区域边界要靠「这一行是否写/读目的寄存器」来判断。首版把**第一操作数一律当写目标**：`ADD r0, r1` 是两操作数形式（`r0 = r0 + r1`），它**读** r0，首版判成只写 ⇒ 区域提前结束，该行不参与改名 ⇒ 这一行读的仍是低位寄存器里的旧值。方向反过来也危险：把读改写成只写会让缓存寄存器与低位寄存器分叉。

定稿规则：**第一操作数之外的每个操作数都算读**；第一操作数在**两操作数数据运算形式**（`ADD/SUB/AND/ORR/EOR/ADC/SBC/RSB/RSC/MUL/MLA/BIC/ORN/LSL/LSR/ASR/ROR/RRX/MVN/NEG`）下也算读，其余（`LDR`/`MOV`/`MOVW`/`MOVT`/`LDRB`…）只算写。宁可多判一次「读」（多一次改名），因为改名的代价只是把同一个值再搬到缓存寄存器，漏判的代价是错答案。

**12.4.4 原地重命名会覆盖仍在读的文本**

`r8` 比 `r3` 长一个字符。第一版在同一个缓冲区里把 `r3` 就地替换成 `r8`，第二次改名再从那片已经被拉长/改写的文本里读 ⇒ 越界或错位。修法是**双缓冲 ping-pong**：`line → rl → rl2 → …`，读一个缓冲、写另一个，最后把 `res` 指针指向最后写成的那个。

### 12.5 口径与不变的纪律

- S6a / S6b 的度量都在**最终二进制**上重跑，不用中途读数。
- 所有门禁走 `tests/` 里的 `build()` 助手构造命令行，不手拼参数，避免夹具与门禁口径分叉。
- `-fopt-vreg` 仍**默认关**，`ARKCC_FEATURE_VREG=0` 的构建按名拒绝（C3900U），不带旗标时十六开关输出逐字节不变（95/95 identical）。
- 本节只追加实测与实现，§5 的七条冻结门禁与 §6 的 F1–F4 否证线**一字未改**；S6c（跨 `BL` + spill，收支判据）仍未启动。

## 13 落地实测（2026-11-24，S6c：区域跨过 call，以及被新夹具顶出的两个真缺陷）

### 13.1 改动：调用不再是墙

S6b 把区域从「下一条指令」放到「基本块余部」，但 `BL`/`BLX` 仍是硬屏障。S6c 只放行一种情形：**被改名的那条 load 的目的寄存器是 `dr`，且 `dr >= 4` 并且它在本函数序言的保存名单里**（`saved_mask`，在预扫描里从 `PUSH {...}` 逐寄存器取出）。理由是逐条可查的：

- 缓存寄存器（`r8-r11`）是 callee-saved，本函数的序言也真的保存了它（否则本 pass 不会拿它做缓存）；
- 未 taint 的槽的地址从未外流，被调用者根本碰不到它——它不在栈上任何可寻址的位置；
- 因此跨过一次调用之后，缓存寄存器里的值与被改名前的 `dr` 一致。

实现上是新增一个屏障等级 `vg_lk = 5`：IT 覆盖扫描与其它所有消费者仍然把 3 和 5 一样当墙（`>= 3`），只有 Pass 2 的区域扫描区分二者：

```
if (vg_lk[j] == 4) break;                   /* 帧建立，仍然是墙 */
if (vg_lk[j] == 5) {
    if (dr >= 4 && ((saved_mask >> dr) & 1u)) continue;   /* S6c：跨过去 */
    end = j; break;                          /* 否则区域在此结束 */
}
if (vg_lk[j] == 3) break;                    /* 其它任何屏障 */
```

**没有放行**「跨 `POP {dr}`」：`POP` 若落在 `dr` 上会静默改掉「`dr` 仍持有该槽的值」这个前提，与本规则无关。

### 13.2 新夹具 `crossbl`

`tests/run_vreg_tests.py` 新增第 9 个夹具：`s` 在**调用之前**写、在**调用之后**读，被调函数故意大到不能内联。断言分两层：

- 通用层（7 条）：不增加指令、`PUSH`/`POP` 增加同一组寄存器、被提升的函数确实要了寄存器、帧基址以上的偏移同步移动、确实消掉指令、三臂（off / on / alone）在模拟器上返回同一个值（219）、`alone` 臂也正确；
- S6c 专属层：`BL` 之后三条指令内，plain 臂**必须**仍有一次 `LDR rN, [r6, #off]`（证明这段 reload 就在调用另一侧），promoted 臂**必须**一次也没有（证明值留在缓存寄存器里、没有回来读帧）。

### 13.3 两个真缺陷（S6b 时期就存在，只是没有夹具）

`crossbl` 一上就跑出**两个错答案**（`on` 臂先返回 889、修一处后变成 141）。两者同源：**改名把值搬进缓存寄存器，而 `dr` 从此不再持有该值**——只要区域边缘有一个「不点名的读者」，这个值就丢了。

**13.3.1 `hits == 0`：区域里没有任何一行读 `dr`**

`n = vg_work(n, 5)` 里，参数 `n` 的 load 后面紧跟 `BL`。S6c 之前 `BL` 是墙，区域 `[i+1, end)` 里没有一行提到 `r0`（`BL` 只是**隐含**读 `r0-r3`），可是 `vg_cons[i] = end` 依然成立，于是 `vg_act[i] = 1` 把 load 删掉、却没有任何一行被改写成读缓存寄存器 ⇒ `r0` 仍然是上一条语句的值（`s` = 41 被当成参数传进去）。修法是新增 `hits` 计数：**只有区域内真的记录了至少一次改名，才允许删 load**；否则退回 `MOV rD, rC`（与 load 同为一条，等于没优化，但答案对）。

**13.3.2 三个隐式读者**

`hits` 只挡住「一行都没改」的情形。真正的一般条件是「区域边缘没有人**隐含**读 `dr`」，而隐含读者恰好有三种，都不是 S6b 的改名能覆盖的：

| 形态 | 谁在隐含读 | 实例 |
|---|---|---|
| 调用 | `BL` 的 `r0-r3` | `n = work(n, 5)`：参数就是那条 load 的值 |
| 压栈 | `PUSH {...}` / `STM...` 名单里的 `dr` | 名单在花括号里，改名逻辑不碰 |
| 返回 | 尾声里的 `r0` | `return t & 0xff` 被改名成 `AND r9, r9, #255`，函数返回的是旧 `r0` |

修法是一个登记位 `vg_rf[i]`（此 import 里原本空闲的数组）：Pass 2 算完 `end` 之后，如果 `end` 是 `BL` 且 `dr <= 3`、或 `end` 是 `PUSH`/`STM` 且名单里有 `dr`、或 `dr == 0` 且从 `end` 一路到帧尾声（`MOV sp, r6` / `ADD sp` / `SUB sp` / 共享返回标签之后）只有拆帧指令，就把这条 load 标成「必须留在 `dr`」——**整条区域一个改名都不做**，直接 `MOV rD, rC`。为什么必须连改名一起放弃：`MOV` 只落在 load 的位置上，若区域里的消费者仍被改写成写缓存寄存器，那么 `dr` 拿到的还是改名前的值，错得更隐蔽。

即 `-fopt-vreg` 现在真实贡献 **−683 条（−4.6%）/ −90 B**（§14 的 `vg_hi_mask` 修复把十八开关从 14,218 抬到 14,271，十七开关不受影响，因为它不含 vreg）。

### 14 `vg_hi_mask` 恒空：vreg 与常量缓存抢 `r8-r11`（0.9.1-wip 修复）

§13 修的是「区域边缘丢值」，这一节修的是另一种更安静的错：**两个消费者同时认为自己拥有同一个寄存器**。

**症状**：十九开关下 95 TU 语料里出现 4 处重复寄存器名单——`PUSH {r5, r6, r7, r8, r9, r8, r9, lr}`
与同形 `POP`（`stm32f4xx_hal_rcc.c` 的 `HAL_RCC_OscConfig` 及其后一个函数、`stm32f4xx_hal_rcc_ex.c`
两处）。内建汇编器对重复寄存器**静默去重**，于是实际压栈字数比 `saved_words` 少，帧偏移与
8 字节对齐的账一起算错。

**根因**：`vg_hi_mask()` 判 token 边界用的是「`r` 后一个字符是否非字母数字」，可那个字符
永远是数字（`r8` 的 `8`），条件恒假 ⇒ 掩码恒为 0 ⇒ `-fopt-vreg` 认为 `r8-r11` 全空闲。
而 `-fopt-regalloc`（含其内置的常量缓存，`CC_MIN_COUNT = 5`）在 vreg **之前**运行，早已
按槽收益占用了其中若干个。两个 pass 各自记账、互不知情。

**修法（三处，后两处是保险）**：

1. 按 token 扫描重写 `vg_hi_mask()`：前一个字符非字母数字、后一个字符非字母数字才算一次
   `rN` 提及，与 `cc_line_hregs()` 同规则（`r8`–`r11` 才置位）。
2. 预扫描之后追加 `used_mask |= saved_mask`：**prologue 里已经保存的寄存器天生在用**，
   这条不依赖上面的扫描是否完备。
3. `pushline` 记下 prologue 的 `PUSH` 行，新增 `ra_names_reg()`，在取新寄存器前把
   prologue 名单里已出现的寄存器从候选里剔掉。当前 prologue 形状（`PUSH {r5,r6,r7,lr}`）
   下不会触发，留着是给「prologue 变宽」留的保险。

**代价与读数**：把抢来的寄存器还回去不是免费的——十八开关 14,218 → **14,271**（+53 条 /
+42 B），十九开关 13,517 → **13,566**（+49 条 / +48 B）。多出来的是原本被错误「省」掉的
帧访问，不是新开销。

**门禁**：新增 `mixed` 夹具——这是唯一能让两笔收益同时成立的形态（同一函数里某个常量
被连加 5 次、又有帧槽被读多次），并给每个夹具的两臂都加了一条通用断言
**「任何 `PUSH`/`POP` 名单里不得出现重复寄存器」**。`mixed` 上有 8 条专属断言，其中
`the constant cache keeps its register and this pass takes a different one` 直接盯住
「两者拿到不同寄存器」。整套 10 个夹具 75 条断言全绿。



## 15 S6b-2（块间活跃性）的实测上界与收档

S6b 做的是**块内**全量重命名；把重命名扩大到「块间」是 S6b-2 的范围：只有当一条
`MOV rD,rS` 的目标在**本块剩余部分**已经没人读、但仍出现在本块的 `live_out` 里时，
跨块活跃性分析才有活可干——这构成了这一项收益的**上界**。

**口径（`D:/tmp/fr/s6b2_bound.py`，未入库）**：按 `.type` 切函数 → 按标签/分支切基本块
→ 逐块算 def/use → CFG 活跃性定点（最多 50 轮）→ 反向扫描每块，统计
「`MOV rD,rS` 且 `rD != rS`、`rD` 不在本块后续任何 use 里、`rD` 在 `live_out` 里」的条数。
不确定的地方一律算「活」（未知助记符视作读遍所有操作数、写空集），所以这个数是天花板。

**自检（证明口径对得上分类器）**：95 TU 共数出 **13,116** 条指令、**1,571** 条
`MOV rD,rS`——与 `docs/BOUNDARY.md` §2 的合计、§5.4 的寄存器拷贝条数**逐条相同**
（这两个数在 §16 的第二次活跃性落地后重测；S6b-2 的判定本身与语料快照无关）。

**结果**：候选 **245 条**，占全部指令 **1.87%**，占寄存器拷贝本身 15.6%。另一条更弱的折叠
（`MOV rD,rS` 紧跟一条只读 `rD` 且 `rD` 在本块之后不再被读）只有 **32 条 = 0.24%**，一并收档。

**判定**：按 F1（收益 < 5% 即收档）**收档**，S6b-2 不实现。剩余 1,326 条拷贝（1,571 减 245）在本块内
就有消费者，删它们必须动值栈/分配模型（与 S6c 之后的 `PUSH {… r0 …}` 问题同属一类），
不在寄存器拷贝这项预算里，已登记。

## 16 第二次活跃性（litpool 之后）与被它顶出的第五个真缺陷（0.9.1-wip）

### 16.1 同一套 L1/L2 为什么值得跑第二遍

**位置**：`ark_emit_program` 的 pass 顺序里放在 `cmat` → `litpool` **之后**、
`ark_fix_far_offset` **之前**，仍是 `-fopt-live` 一个门控（不开这个开关就一遍都不跑，
OFF IS OFF 逐字节不变）：

```c
#if ARKCC_FEATURE_OPT_LIVE
        if (g_config.enable_opt_live)
            ark_live_function(&buf, fstart, ark_ret_mask(f->ret_type));
#endif
```

**理由**：活跃性是一个**关于文本**的判定。第一遍看到的是「cmat / litpool 改写之前」的
文本，它算出来的 `live_out` 在那之后已经不成立——`-fopt-litpool` 把 `MOVW`+`MOVT rD`
换成一条 `LDR rD, .Llit_*`，值栈里那些「材料化完的常量先落 `rD`、再 `MOV` 到使用者」
的拷贝形态整体变了；`-fopt-cmat` 同理换掉了材料化点。第一遍判「活」的一批 `MOV`，
在改写后的文本里目标已经没人读了。

**读数（95 TU，Cortex-M4，`-O2`，十九开关）**：

| 口径 | 指令 | 代码字节 |
| --- | ---: | ---: |
| 只跑一遍（第一遍） | 13,566 | 34,980 |
| 加跑第二遍 | **13,116** | **34,200** |
| 差 | **−450（−3.32%）** | **−780（−2.23%）** |

**省的落点是干净的**：按 `docs/BOUNDARY.md` §2 的十八栏口径逐栏对拍，只有两栏动了——
`MOV` 立即数 1,492 → **1,202**（−290）、`MOV rD,rS` 1,731 → **1,571**（−160），
其余十六栏**一条不差**（含 `PUSH`/`POP` 1,239、帧访问 922、字面量池 705）。这正好对上
「删的全是死拷贝」这个预期：第二遍不做别的改写，只删 `MOV`。

**没有跑第三遍**：第二遍之后文本已收敛到「L1/L2 不动」，但要断言「第三遍一定 0 收益」
需要再改一次代码做对照，本轮没做，**登记为未测**。可以确认的是第二遍本身不是恒等：
它删了 450 条。

**代价**：多一遍 CFG 构建 + 不动点迭代（`ARKCC_FEATURE_OPT_LIVE` 的静态表约 1.5 MB，
板端剖面本来就裁掉整个 pass，所以 MCU 侧没有新增代价）；宿主编译时间增量在语料规模下
落在秒级（95 TU 全量 `-S` 约 20 s 量级）。

### 16.2 顺带被顶出的第五个真缺陷：`ADDS`/`SUBS` 的高寄存器被 `& 7` 掩码

§12.4 那四个缺陷「都是在槽被提升到 `r8-r11` 之后才现形」，这一条同族：第二次活跃性
删掉更多 `MOV` 之后，后端更容易直接产出**高寄存器做加法/减法**的形态（`ADDS r0, r0, r9`），
而内建汇编器的 `ADDS`/`SUBS` 发射器（pass 2）当时对寄存器形式**无条件发 16 位并 `& 7`**：

- **错答案**：`ADDS r0, r0, r9` 编成 `adds r0, r0, r1`——静默算错，不报错。
- **更糟的连带**：pass 1 按 `rd/rn/rm` 全 ≤7 才给 2 字节、否则给 4 字节，pass 2 却恒发
  2 字节 ⇒ 其后**所有标签整体偏移 2 字节**，`wide` 夹具上表现为 `PC=0` 崩溃
  （unicorn `UcError UC_ERR_EXCEPTION`）。

**修法（pass 2 编码器 + pass 1 尺寸表同步）**：

| 形态 | 编码 | 宽度 |
| --- | --- | --- |
| `ADDS`/`SUBS Rd, Rn, #imm3`，三者 `r0-r7` | 16 位 `0x1C00/0x1E00` | 2 B |
| `ADDS`/`SUBS Rd, Rn, #imm8`，`Rd == Rn`，`r0-r7` | 16 位 `0x3000/0x3800` | 2 B |
| `ADDS`/`SUBS Rd, Rn, Rm`，三者 `r0-r7` | 16 位 `0x1800/0x1A00` | 2 B |
| 任一寄存器不在 `r0-r7` 的寄存器形式 | 32 位 `adds.w`/`subs.w`：`0xEB10/0xEBB0 \| Rn`，后接 `(Rd<<8)\|Rm` | 4 B |
| 两操作数 `ADD Rd, Rm`（无 `S`） | 16 位 `0x4400` T2，**任意寄存器** | 2 B |

越界一律报错而不是截断：`imm` 放不进 12 位报 `ADDS/SUBS immediate %s does not fit any
encoding`，`sp` 调整超出 508 字节且非 4 对齐又放不进 12 位报 `sp adjustment of %s bytes
does not fit one encoding`，缺源寄存器报 `%s at code offset %s has no source register`。

**取证（capstone 反汇编，`addsub_high` 夹具）**：

```
0x043e  adds.w r0, r0, sb     4 B
0x0442  subs.w r0, r0, sl     4 B
0x0448  adds.w r1, r1, sb     4 B
0x044c  subs.w r4, r1, sl     4 B
0x0450  adds   r0, r0, r4     2 B
0x0452  add    sb, r0         2 B    ; 0x4400 T2，目标 r9
0x0454  mov    r0, sb         2 B
```

新夹具 `addsub_high` 已进 `tests/arm_exec/run_arm_exec.py`（`main` 返回 `addsub_hi(20, 6)`
= **64**）：`MOV r9/r10` 取参数 → 四条 `ADDS/SUBS` 命中高寄存器 32 位形态 → 一条 16 位
`ADDS` → `ADD r9, r0`（T2）→ `MOV r0, r9`。它同时钉住「32 位形态算得对」与「T2 两操作数
任意寄存器」两条。

### 16.3 装配器两遍尺寸一致性自检（硬错误，不是警告）

这类缺陷的共同形状是「pass 1 算的宽度与 pass 2 发的宽度不一致」，一旦发生，其后所有
标签偏移全错，而**文本本身看不出来**。所以修完不逐条补用例，而是加一条总账自检：

- `ArmAsm` 加字段 `pass1_size`，`pass1_a` 末尾 `a->pass1_size = pc`；
- `pass2_a` 末尾比较 `a->pc` 与 `a->pass1_size`，不等就
  `diag_tool(DIAG_SEV_ERROR, ...)` 报
  `assembler size pass disagrees with the emit pass (%s bytes laid out, %s emitted):
  some line is encoded at a different width than pass 1 counted`，并 `hard_errors++`。

**为什么比总长而不是逐条**：一次比较覆盖整类错配；且它对输出字节零影响（只读）。

**自检必须能失败**：加了编译期探针 `ARKCC_ASM_SIZECHECK_PROBE`（在 `pass1_a` 末尾把
`pass1_size` 人为 `+2`），用 `-DARKCC_ASM_SIZECHECK_PROBE` 构建出的二进制实测报
`(1122 bytes laid out, 1120 emitted)`；正式构建静默通过。用编译期宏而不是 `getenv`，
是因为 MCU 剖面没有 libc 的 `getenv`，探针也绝不能进任何真实构建。

## 17 值栈模型改造的第一小步：`ADD #0` 变 `MOV`，以及最终文本上的第二遍窥孔（0.9.1-wip）

§15 与 §16 都是「把同一个开关再跑一遍」。这一轮换个角度：**不加规则、不加旗标，只把值栈
发射器写出来的、语义上是拷贝而文本上是算术的那一类行，改写成后续 pass 认得的形态。**

### 17.1 为什么改在文本层，而不是发射期

值栈为三件事都发同一条指令 `ADD rD, rS, #0`：`x = y` 这类寄存器拷贝、把帧基址搬进临时
寄存器、零位移的地址材料化。语义上都是拷贝，文本上却是算术。

| 文本 | 字节 | 编码 |
| --- | ---: | --- |
| `ADD r5, r8, #0`（D≠S） | **4** | `addw r5, r8, #0`（`08f1 0005`） |
| `ADD r0, r0, #0`（D==S，且 `rd` ≤ r7） | 2 | `0x3000` 形态（`ADDS r0, #0`，**改标志**） |
| `MOV r5, r8` | **2** | `0x4600` |

`ADD`（不带 `S`）的立即数形式只有 32 位 `ADDW` 一条编码，所以只要 D≠S 就是 4 字节；
`MOV` 寄存器到寄存器恒为 16 位、2 字节，两者都不写标志（见 17.4）。

**为什么不直接在发射期发 `MOV`**：下游两条既有规则只认 `MOV`——`-fopt-live` 的 L1
（`MOV rD, rS` 且 `rD` 之后不活跃 ⇒ 删除）与 `-fopt-coalesce` 的活拷贝前推。两条都在
文本里找 `MOV`，`ADD` 一条也匹配不上。先在文本层改写，这两条规则就自动接管同一批值，
一次改动吃到两级收益：463 条站点里 215 条随后被整行删掉、202 条被前推或保留。

**为什么不新开旗标**：这是纯文本等价改写，与 R1/R3 同族（见 `docs/PEEPHOLE.md`），属于
`-fopt-peep` 的既有职责。不新增旗标 ⇒ 裁切表与 `C3900U` 按名拒绝表一个字不用改，
`ARKCC_PROFILE_STM32_MIN` 剖面下整段照旧被裁掉。

### 17.2 第二遍窥孔（与 §16 的第二次活跃性同构）

R1（`PUSH {rX}` … `POP {rY}` ⇒ `MOV`）在第一遍窥孔跑的时候几乎不匹配：那时栈往返的两端
还是值栈自己挑的临时名，压的和弹的往往不是同一个寄存器。真正让两端**变得同名**的是它
下游的 `-fopt-coalesce` / `-fopt-live` / `-fopt-vreg` / `-fopt-slotreg` 的改名——死对
是**被后面的 pass 造出来的**，所以必须在最终文本上再看一遍。

实测（95 TU，十九开关）：

| 语料 | 相邻 `PUSH`/`POP` 对 | 其中两端寄存器集合相同（真死对） |
| --- | ---: | ---: |
| 改造前（13,116 条） | 34 | **25** |
| 改造后（12,795 条） | 9 | **0** |

最终顺序因此是：第二遍活跃性 → **第二遍窥孔** → `ark_fix_far_offset` → init/fini_array。
窥孔必须排在 `ark_fix_far_offset` **之前**：后者把超远帧偏移改成经 `r12` 的间接访问，
那之后文本里不再有「同一个 `[r6, #off]`」形态可配。

### 17.3 实测数字（95 TU，Cortex-M4，十九个 `-fopt-*`）

| 口径 | 指令 | 字节 |
| --- | ---: | ---: |
| 基线（`a6f3c94`） | 13,116 | 34,200 |
| + R5（关掉第二遍窥孔的隔离构建） | 12,847（−269） | 33,572（−628） |

### 17.4 语义安全：标志位

- **D≠S**：`ADDW` 不写标志，`MOV rD, rS`（`0x4600`）也不写标志 ⇒ 改写前后标志状态相同。
- **D==S**：`ADD rd, rd, #0` 走 `0x3000` 形态，那是 `ADDS`，**会写标志**。删掉它就少了
  一次标志写。方向是安全的：本后端从不跨语句携带标志（每条条件分支前都紧邻自己的
  `CMP`/`CMN`/`TST`/`TEQ`），所以「少写一次标志」既不会救活也不会破坏任何既有依赖。
- **取证**：在改造前的 13,116 语料里扫「`CMP`/`CMN`/`TST`/`TEQ` → `ADD rX, rX, #0` →
  条件分支/`IT`」这一形状，命中 **0 处**；改造后语料 `ADD .* #0` 残留 **0** 条、
  `MOV rX, rX` 自赋值残留 **0** 条（`pp_r5` 只在 D≠S 时发 `MOV`）。

### 18.6 2026-11-24 补记：读-改-写形态的重命名必须能回写

18 节说「改名把本来不可折变成可折」，这一条是它的反例：**`-fopt-vreg` 的重命名
在 RMW 形态上会把临时值留在缓存寄存器里。**

`vg_cons[i]` 扫一个槽的 load 时刻之后，遇到「读又写目的寄存器」的行（`ADD r0, r0, #1`
这类）时原来一律把它算作可继续的重命名窗口。但重命名的前提是**缓存寄存器在此后一直
承载该槽当前的值**；RMW 之后寄存器里是「运算结果」而不是「槽的值」，只有当这条结果
紧接着被写回同一个槽（计数器惯用法 `LDR r0; ADD r0,#1; STR r0`，写回行会被改写成自
移动）时才等价。

反例是 `stdlib` 的 `mul32x32`：`a0*b0` 与 `a0*b1` 共用 `a0`，两个结果各自写进自己的
槽。旧版把 `MUL r10, r1` 重命名后又用同一缓存寄存器算第二个乘积，于是第二次乘法把
`p00` 乘成了 `b1`——`-fopt-pair -fopt-vreg -fopt-vstack` 三开关下 `shift64` 用例回
`0` 而不是 `50`。

修法：RMW 之后先找它的下一条指令，**只有**当下一条正好是「把同一寄存器写回同一槽」
（`vg_lk[q] == 2 && vg_lo[q] == s && vg_dr[q] == dr`）才继续重命名；否则退成 act 2
（保留 `MOV rd, rC`，代价与原来的 load 相同）并把区域在 RMW 之前截断，区域内的东西
一个都不改名。宁可少改名，不给错答案。

验证：`m32.c` 最小复现、三开关 / 五开关、`one.py shift64` 与 23 开关全量
`tests/arm_exec`（40/40）全绿；95 TU 体积无回归（该形态在 HAL 语料里没有命中）。

（多省 8,650 B）。这正面否掉了「两者抢同一批栈往返、叠加为负」这条 P12 S5 的原判前提。

### 19.3 逐 TU：四个方向都是零变大

| 比较（谁被打开） | 变好 | 不变 | 变坏 |
| --- | ---: | ---: | ---: |
| 加回 vreg（去 vreg → 全开） | 14 | 81 | **0** |
| 加回 vstack（去 vstack → 全开） | 17 | 78 | **0** |
| 只加 vreg（两个都去 → 去 vstack） | 17 | 78 | **0** |
| 只加 vstack（两个都去 → 去 vreg） | 10 | 85 | **0** |

P19 冻结判据里的「任一 TU 变大即红」一条都不触发。95 个 TU 中 vreg 只在 14–17 个上有动作、
其余逐字节不变，这与 §11 记的「vreg 覆盖面窄、单点收益大」一致。

### 19.4 为什么是超可加

两个 pass 吃的是同一大类（栈往返），但作用对象不同：

- `-fopt-vstack` 改的是**表达式求值中途**的值栈影子槽（`r5`/`r7`/`r4`），把 `PUSH {r0}` /
  `LDR/STR [sp]` 换成寄存器；
- `-fopt-vreg` 改的是**局部变量槽**的 load/store 提升，池是 `r8`–`r11`，且刻意排在
  `-fopt-regalloc` 之后（`backend_arm.c` 调用点注释：两者共用一段 PUSH/POP 保存块和一个基址，
  谁也不是谁的屏障）。

顺序上 `vreg` 跑在 `vstack` **缩短之后**的文本上：vstack 先把值留在池寄存器里，
槽访问的形状随之变少变窄，vreg 的重命名窗口更容易成立——这与 §18.5 记的「改名把本来不可折
变成可折」是同一类机制。**（超可加的这部分归因是按遍历顺序推的，未做逐函数取证；
「两条都留」这个判决本身不依赖这条归因。）**

### 19.5 「合并去重」这一半为什么不做

S6d 的名字里有「合并去重」，这一半按同一套 F1 口径**收档，不动代码**：

- **裁切剖面零成本**：`ARKCC_PROFILE_STM32_MIN` 下 `ARKCC_FEATURE_OPT_VSTACK` 与
  `ARKCC_FEATURE_OPT_VREG` 都是 0，两个 pass 整体被编译掉。最小板上剖面上一分钱也省不到。
- **非最小剖面的上界**：x86-64 `gcc -O2` 单编 `backend_arm.c` 量静态符号，
  `ark_vreg_function` 7,792 B + `vg_*` 辅助约 2.6 KB，`vs_*` 辅助约 4.2 KB。两套文本行解析器
  （`vg_flatten`/`vg_mnem`/`vg_slot`/`vg_is_frame_*` 对 `vs_parse`/`vs_form`/`vs_masks`/
  `vs_read_before_write`）确有同构重复，但**可共享的部分上限是两套里较小的那一套（约 2.0 KB）**，
  实际远小于此——`vs_*` 要操作数形态与读写掩码表，`vg_*` 要帧偏移/标签/展平，语义本就不重合。
- 对照板端 `stm32_build_check.py --layout sdram` 的 `code 349,466 B`，2.0 KB 约 **0.6%**，
  而代价是重构两个已经各自被真缺陷教训过的 pass（§18.6 刚修过 vreg 的 RMW 回写）。
  按「风险成本 > 收益」收档；登记为「将来若要压**编译器自身**体积再评估」。

### 19.6 落地动作

- 代码：**零改动**。两个开关照旧各自独立、可任意组合，默认仍关（`-fopt-*` 逐个开）。
- 文档：本节 + `docs/OPTIMIZER_PLAN.md` P19 状态行（中英双份）。
- 复现：用 §19.1 的四组选项各跑一遍 95 TU 就能重出上表。四个组合取自**同一份二进制**，
  节内所有差值因此只反映开关、不反映构建。
- 与 §18.5 那两张表的读数不可相减：本节的全开是 **12,239 条 / 405,426 B**，§18.5 记的是
  12,266 条 / 405,514 B（再到第二遍 `cbz` 的 404,970 B）。差的 27 条 / 88 B 来自**构建不同**
  ——本节用的是 `36ac163` 之后（浮点字面量精确化已并入）的 `arkcc.exe`，字面量按新口径
  精确舍入后个别常量与常量折叠结果随之变化。跨节比较必须同构建重跑，不许互减。
