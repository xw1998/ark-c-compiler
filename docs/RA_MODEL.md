## 3 目标模型：分配单位从文本行换到 IR 虚拟寄存器

今天的样子（`docs/RA_VSTACK.md`）：IR 里每个表达式节点**真的压一次栈**，后端按行发射，
值栈 pass（`-fopt-vstack`）在**文本上**做影子栈改名，池只有 2–3 槽，边界一律清空。
S6 系列（`-fopt-vreg` / `-fopt-slotreg`，`docs/VREG.md`）已经把「文本层改名」做到头：它
能删冗余搬运，但**决定不了「值出生在哪个寄存器」**——那在发射时就已经写死了（`r0`）。

目标模型只有一句话：**发射期就给每个 IR 值一个虚拟寄存器，分配在 IR 层完成**。

```
值 v 的一生：  def 在一个 IR 指令上 → 活跃区间 [def, last_use]
分配：        线性扫描（Poletto & Sarkar），可用寄存器 r4–r11（8 个，callee-saved）
              r0–r3 留作参数/返回值与「区间不跨越调用也不跨越分支」的短命临时
帧槽：        只有两类对象留在 [r6, #o]：spill，以及地址被取走的变量
边界：        块内分配为主；跨块（join）沿用 `docs/VSTACK_CFG.md` §3 的保守判据
```

为什么这是「换模型」而不是「再加一条 pass」：

- 今天的 FRAME 926 条差额与 MOVREG 1,101 条差额是**同一个决定**：值出生在 `r0` 且必须
  先落内存。文本层再怎么改名，也改不动「它在 `r0` 里出生」这件事。
- 反过来，只要分配器能在发射期说「这个值就住在 `r7`」，`MOV`/`STR`/`LDR` 三族的相当一部分
  **根本不会产生**，而不是产生后被删掉。这正是 `docs/BOUNDARY.md` §4 三条结构性原因的根。

### 3.1 IR 的今天：纯栈机，没有虚拟寄存器字段（订正）

预注册第一版在这里写错了一句「S6 已经把每个值编号」，实际代码不是这样，2026-11-25 复核：

- `include/common.h` 的 `IrOp` 是**纯栈语义**——`IR_PUSH_INT` / `IR_PUSH_VAR` /
  `IR_BINARY`（注释原文：「pop right operand r1, left operand r0」）/ `IR_STORE` …，
  每条指令的输入输出都在**隐式栈顶**；
- `include/ir.h` 的 `IrInst` 只有 `op / val / name / aux / line / aux2` 六个字段，
  **没有虚拟寄存器编号**，也没有活跃区间；
- `-fopt-vreg` 的实现 `ark_vreg_function()` 在
  `src/backend/arm/backend_arm.c:3794`（调用点 14713），它拿到的是**已经发射完的
  `AsmBuffer`**，做的是文本层的寄存器改名；`-fopt-slotreg` 同理。
- IR 也没有 dump 选项（没有 `--dump-ir` 之类），所以也没有「读 IR 做离线分析」这条路。

因此 **S6 系列不是「IR 级编号」，而是「发射后的文本层改名」**，目标模型（§3 的线性扫描）
仍然是**未实现**的；而 S8b 的第一步就必须是「给 `IrInst` 加 vreg 字段 + 让 IR 生成器
按值分配编号 + 加 IR dump」，那本身就是模型改造的一部分（工作量在分配器之外）。

已经就位的零件（不必重做）：常量池（`-fopt-litpool`）、基址复用与寻址折叠
（`-fopt-addr`）、强度削减（`-fopt-strength`）、比较直连分支与 `CBZ`、尾调用与块尾合并、
`--size-weight`。

缺的只有一件：**分配器本身**（以及它要求的 IR 改造）。

### 4.1b 地址链折叠：不是新族，是 `-fopt-addr` 的覆盖缺口（补完，兑现 100 条）

S8a 量上界时顺手扫出一批「基址形成之后没被折掉」的形态，以为是一族新的东西。核对
`ark_addr_function()`（`src/backend/arm/backend_arm.c`）之后要纠正：`-fopt-addr` 的
R1/R2/R3 **本来就在折** `ADD RD, RB, #imm` / `ADD RD, RB, RI` / `MOV RD, RS` 之后紧邻的
访存。量到的 189 条是**覆盖缺口**留下的余量，缺口有两个：

| 缺口 | 形态 | 条数 |
| --- | --- | ---: |
| 访问不必紧邻 | `ADD rD, rX, #k`（或 `MOV rD, rX`）之后隔几条才用 `[rD, #j]` | 189 |
| `MOV` 后面不是访存 | `MOV rD, rS` + `ADD/SUB rD, rD, #k`（R1b 补完后才显形） | 38 |

补法是**扩 `-fopt-addr`**，不新增开关、不加裁切行（整段本来就在
`ARKCC_FEATURE_OPT_ADDR` 里）：

- **R1b（前瞻折基址）**：`ADD RB, RS, #imm` 之后在 4 条指令内找第一条「以 RB 为基址、
  无索引寄存器」的访存；窗口遇 label、条件指令、`B/BX/BL/BLX/CBZ/CBNZ`、对 RB 或 RS 的写、
  对 RB 的非访存读即关闭；折之前仍按 R1 的死亡条件收尾（写回 RB，或 RB 之后已死）。
- **R0（把 MOV 并进算术）**：`MOV RD, RS` 紧跟 `ADD|SUB RD, RD, #imm`（imm 取 0..4095）
  ⇒ 一条 `ADD|SUB RD, RS, #imm`。MOV 在被覆盖的瞬间死亡，**不需要活跃性检查**；标志位与
  结果都还是原来那条 ADD/SUB 产生的。

实测（26 旗标 95 TU，`D:/tmp/bm/remeasure.py`）：

| 阶段 | 指令 | 字节 | 相对改前 |
| --- | ---: | ---: | --- |
| 改前（`e295220` 的 26 开关产物） | 11,766 | 398,673 | — |
| + R1b（前瞻折基址） | 11,713 | 397,686 | −53 / −987 |
| + R0（MOV 并入算术） | **11,666** | **396,986** | **−100 / −1,687** |

**预测量 189、实际只兑现 100，差额全部落在「块尾死亡」**：`ad_dead_after()` 遇到 label /
分支 / 调用一律返回「活」，因为文本层不知道块尾会流到哪个后继块。把这条放宽，就等于让
pass 去赌一个它证不了的活跃性——「宁可报错，不给错答案」不允许这么做。这个落差本身就是
结论：**文本层能安全兑现的地址折叠已经吃完**，剩下的要等「块内活跃性」这个东西存在，也就是
S8b 那份分配器；而 §4.1a 已经判它自己打不过 armcc。

残形复查（`addrchain_ac.py`，对改后产物重扫）：`MOV + ADD-self` 剩 **0**、`ADD` 基址 +
`[rD]` 剩 **0**。门禁 `tests/run_addr_tests.py` 全绿，含 OFF IS OFF 与四条模拟器执行臂。

### 4.2 S8b：实现（新开关，默认关）

## 6 反假绿对照

三条，写死：

1. **强制单寄存器**：分配器实现之后加一个编译期探针 `ARKCC_RA_FORCE_R0`，让所有值都分到
   `r0` 并按今天的规则落内存——其 95 TU 产物必须与**今天逐字节相同**。这条证明的是
   「收益来自分配」，不是「重写之后恰好少了两条指令」。
2. **与 `-fopt-vstack` 的叠加必须非负**：`ra-model` 打开后，`-fopt-vstack` 的增量不得为负
   （模型改造吃掉的正是 vstack 的地盘，若叠加反而变差，说明两者在抢同一批站点且互相打架）。
3. **不许用 `MOVREG 总数` 当收益**：删掉一条 `MOV` 很可能引入一条 `LDR`（`docs/VREG.md`
   §18.3 的 1,178 就是这类「看起来是收益」的数）。判定只看**指令总数与字节总数的双向读数**。

## 10 0.9.1 的最终账：打到 5,619 需要消掉什么

把 §1 的差值表和 §4.1 的上界放在一起算，答案很清楚：**这不是分配器能补的差距**。

| 差额来源 | 条数 | 谁来吃 | 实测可兑现 |
| --- | ---: | --- | --- |
| MOVREG +1,101 | 1,101 | 分配器（值不再生在 r0） | 266（2.26%） |
| PUSHPOP +1,013 | 1,013 | 分配器（不留栈池） | ≤636 里的一部分 |
| FRAME +926 | 926 | 分配器（局部不进帧） | 165 块内 + 718 跨调用（后者净 220） |
| MOVIMM +804 | 804 | 部分靠分配器复用零/一 | 未量，按复用率 30%–50% 估 240–400 |
| MOVW/MOVT +338 | 338 | 常量池（已有 `-fopt-litpool`，剩的是池化收益边界） | 未量 |
| POOL +314 | 314 | 同上 | 未量 |
| ARITH +520 | 520 | 地址链折叠（4.1b 已兑现 100）+ 表达式模型 | 100（0.85%，已落地） |
| LOGIC +338 / MEM +539 / BR +250 / CMP +199 | 1,326 | 表达式与分支模型 | 未量 |

**合计可兑现（今天的树上能证的部分）约 1,100–1,400 条 = 9%–12%**（其中地址折叠那 100 条
已经在本轮兑现），落到
**10,000–10,600 条 = 1.8×–1.9×**。要真正打到 5,619，需要把六族里**每一族都削掉一半以上**，
那不是「换分配单位」，是**重写表达式与常量的求值模型**（每个 C 表达式从「压栈—弹栈—
r0 往返」换成「直接算进目标寄存器」）。这条工作量的量级比 S8b 大一个数量级，且
`docs/BOUNDARY.md` §3 已写死「不得以 armcc 的指令构成为目标反推规则」。

结论写死三句：

1. **0.9.1 的优化线到此收官**：26 开关口径 **11,666 条 / 396,986 B**，对 armcc `-O2`
   **2.08×**（指令数），文本层九族残形合计 167 条（1.42%，改前口径）已全部收档，
   地址折叠缺口本轮补完兑现 100 条（0.85%），残形归零；
2. **模型改造（S8b/S8c）记为 `ceiling_insufficient`**：上界 15.2% 全部吃掉也只有 1.78×，
   而块内可兑现部分 < 5%；
3. 真要再进一步，入口是**表达式求值模型**（不是分配器），且必须新开预注册、重新冻结判据。
