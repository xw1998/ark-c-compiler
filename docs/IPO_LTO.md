
# 全程序编译（`--ipo` / `-flto`）

[English](IPO_LTO.en.md) | 中文

0.8.7 加了 `--ipo`（别名 `-flto`）：**一次调用吃多个 `.c` 文件，产出"一个程序"**。
它不是在链接器里做的 LTO，原因在 §1；它能做到的事在 §3 说清楚，做不到的事在 §6
逐条列出，不用"近似 LTO"含糊带过。

| 开关 | 默认 | 剖面 | 要求 |
| --- | :---: | --- | --- |
| `--ipo` / `-flto` | 关 | `full`（MCU 最小剖面不含） | 必须给 `-o` |
| `ARKCC_FEATURE_IPO` | 宿主 `1`，`ARKCC_PROFILE_STM32_MIN` 为 `0` | 裁剪开关 | 可在命令行 `-DARKCC_FEATURE_IPO=0/1` 覆盖 |

`--ipo` **只改变分析范围，不改变 `-O` 语义**：想拿到跨文件内联，仍然要给 `-O2`
（或 `--autoinline`），和单文件时一模一样。

---

## 1. 为什么不是"对象级 LTO"

真正的 LTO 要能在链接期重新优化：链接器拿到每个对象里的中间表示，合并后再跑一遍
优化和代码生成。本项目的对象格式是 `ARKOBJ2`：

```
"ARKOBJ2\n" | u32 代码长度 | 代码字节 | 符号表 | 重定位表（4=绝对、5=PC 相对）
```

**对象里没有 IR**。要做真 LTO 就得给对象加一个 IR 载荷段，再让链接期把 N 份 IR
重建、重编号字符串/浮点/标签池、重跑后端——那是另一套契约（对象格式、链接器、
调试信息、版本兼容都要改），而且"链接器里能不能跑一个完整后端"这个前提本身
就要先在板上验证。

所以这一版做的是**编译期 whole-program 编译**：编译器在同一个进程里读完所有
源文件、在同一个 `IrProgram` 里做完所有跨文件优化，再一次性生成代码。它对用户
看到的形态就是"多个源文件 → 一个镜像"，但机制与链接期 LTO 不同，产物也不同
（`--ipo` 不接受 `-c`、不接受 `-link`）。

## 2. 用法

```bash
# 两个源文件合成一个镜像（最常用）
arkcc --ipo main.c util.c -target arm --cpu Cortex-M7 -O2 --vector-table -o app.bin

# 只看合并后的汇编（跨文件内联的证据在这里）
arkcc -flto main.c util.c -target arm -O2 -S -o merged.s
```

必须满足：

- **给 `-o`**：多输入时没有唯一的名字可以派生输出名，缺了直接拒绝；
- **输入必须是 C 源**：`.s`（汇编）与 `.o` / `.ark_obj`（对象）会被点名拒绝，
  后者要的是 `-link`；
- `-c` / `-E` / `-g` / `-link` 一律拒绝，理由见 §5。

单文件也能用 `--ipo`：那种情况下产出与普通编译**逐字节相同**（门禁里有对拍），
因为合并、去重、剪枝对一个文件都没有可做的事。

## 3. 合并语义

每个文件仍然**独立走一遍前端**（预处理 → 词法/语法 → 语义 → AST 检查），
然后在同一个 `IrProgram` 上**追加**它的 IR。这样做而不是"先各自生成再合并两个成品
program"，是因为 IR 的字符串池、浮点池、标签号都是**索引寻址**的，合并成品要么重编号
（风险高、错了会静默串常量），要么改池的所有权模型。

追加带来的两个直接问题，各有一条规则：

### 3.1 文件作用域符号改名

C 里两个文件各自的 `static int step` 是**两个不同的函数**。分成两个对象时这件事
由链接器天然保证（每个对象的本地符号互不相干）；合并进一个 program 之后这条边界
消失了，所以必须写进名字里：

```
static int step(...)         ->  __ipo0f_step        (第 0 个文件的函数)
static int table[4];         ->  __ipo1g_table       (第 1 个文件的对象)
```

生成的名字会**在全程序范围内查重**；万一撞了（比如用户自己写了 `__ipo0f_step`），
就再加一个 `_` 直到不撞。加不出来（64 次都不行）时报错并拒绝，不赌。

改名只改**这 5 个携带符号名的 opcode**：`IR_CALL`、`IR_PUSH_FUNC`、
`IR_PUSH_GLOBAL`、`IR_STORE_GLOBAL`、`IR_PUSH_GLOBAL_ADDR`，外加
`IrFunc.alias_target`、`IrGlobal.init_sym`、`init_refs[].sym`。
其余带 `name` 字段的 opcode 语义不同，**碰到就是错答案**：

| opcode | `name` 里到底是什么 | 处理 |
| --- | --- | --- |
| `IR_PUSH_STR` | 字符串的字节 | 不动 |
| `IR_LABEL_NAMED` / `IR_JMP_NAMED` | `goto` 标签（后端已按函数前缀区分） | 不动 |
| `IR_ASM` | 汇编文本 | 不动（见 §3.3） |

### 3.2 外部名解析

同一名字出现多次时，按链接器的规则裁定：

| 形态 | 结果 |
| --- | --- |
| 两个 `static` | 已改名，各自独立（见 §3.1） |
| 一个 strong + 若干 weak 函数 | strong 胜出 |
| 多个 weak 函数 | 保留第一个 |
| **两个 strong 函数** | **报错**：`multiple definition of function 'x' across the --ipo inputs` |
| `int g;` 出现两次（tentative） | 合并为一个对象（C 6.9.2p2） |
| `int g = 1;` 出现两次 | **报错**：`multiple definition of 'g' ...` |
| `extern int g;` + `int g = 1;` | 定义胜出，初始化器保留 |
| 只有 `extern int g;`（无人定义） | 留一条 extern；代码生成时若仍有引用，镜像构建会拒绝（不会静默出镜像） |

这些裁定**必须做在优化之前**：把两个同名 strong 函数丢给后端，得到的是两个同名标号，
链接期行为取决于汇编器，可能安静地绑成一个。

### 3.3 剪枝：只删"可证明无用"的

跨文件内联之后，某些 `static` 函数已经没人调用了；分成对象编译时链接器也删不掉它们
（对象里没有"未使用"这个信息），所以合并后删掉能省体积。剪枝的保留清单是硬的：

- `used`、`constructor`、`destructor`：定义本身就是用途；
- `alias_target`：有别的符号在指它；
- 对象上的 `__at()`（`has_at`）与 `section`：位置是外部可观测的；
- **整个程序里出现任何 `IR_ASM`** → 整段剪枝跳过。汇编文本里的符号名不做解析，
  猜错就是静默错答案。

先删函数，再重新计算引用，然后删静态对象——否则"只被死函数引用的对象"会被误判。

## 4. 流水线只跑一次

这是 `--ipo` 全部价值的来源：`pipeline_run_ir()` 在**合并后的整个 program** 上跑
一次，而 `ir.inline` 本来就是全程序 scope（`opt_inline(prog)` 按 `prog->funcs[]`
查表）。所以只要多个 TU 的 IR 在同一个 program 里，**跨文件内联就是免费的**，
不需要新写一条 pass。

实测（`tests/run_ipo_tests.py`）：`main` 调另一个文件里的 `one()`，`-O2` 时汇编里
没有 `BL one`，`-O1` 时有——因为 `ir.inline` 的 `min_level` 是 2，这一点和单文件
完全一致。

## 5. 拒绝的组合与理由

宁可拒绝，不给"看起来能用"的半成品：

| 组合 | 理由 |
| --- | --- |
| `--ipo -c` | 一个对象装 N 个 TU 要回答"单元 A 里未定义的外部在单元 B 里有定义"在对象层意味着什么（今天是"一条重定位"），而且每单元的 static 改名后链接器无法还原。这是另一套契约，不是这一版 |
| `--ipo -E` | 预处理本来就按文件做；要展开就对每个文件分别 `-E` |
| `--ipo -g` | 合并后的 program 只有**一个** `source_file`，硬塞会让所有单元的行号都挂到第一个文件名下——这是错答案，拒绝 |
| `--ipo -link` | `-link` 吃对象，`--ipo` 吃源文件 |
| `--ipo` 缺 `-o` | 多输入没有唯一名字可派生输出名 |
| `--ipo` 输入是 `.s` / `.o` | 汇编没有可解析的内容；对象没有 IR（那是 `-link`） |

## 6. 已知局限

- **不是对象级 LTO**：不能对第三方提供的 `.ark_obj` / `.a` 做跨边界优化；要优化
  就必须拿到源码。
- **没有跨 TU 常量传播 / 全局变量定理**：合并只让已有的 pass 看见更多代码，
  这一版没有新写任何"跨 TU 专属"变换。
- **`-g` 不支持**（§5）：调试信息仍按单文件编译获得。
- **`-MMD` 输出名**：合并时各单元写同一份依赖文件，后写的赢；多文件生成依赖请
  对每个文件分别 `-MMD -MF`。
- **内存**：所有单元的 IR 同时驻留。宿主池 64 MB 够用，板端 128 KB 不够，所以
  STM32 最小剖面把 `ARKCC_FEATURE_IPO` 关掉——关掉时 `--ipo` 会明确报
  "not compiled into this build"，不是"未知选项"。
- **体积与时间**：合并后一次优化一遍，`-O2` 下体积按内联阈值增长，这是与单文件
  编译相同的取舍，不是 `--ipo` 引入的。

## 7. 门禁（`tests/run_ipo_tests.py`）

`make test-ipo`。十九项检查，覆盖四类：

| 组 | 检查 | 为什么这一项能失败 |
| --- | --- | --- |
| 动态（ARM 模拟器） | 跨文件调用返回 28 | 合并错名字就返回别的数 |
| 动态 | 两个文件各有一个同名 `static`，结果 23 | 改名没做 → 撞名（错误）或取错那个（错值） |
| 动态 | 两个 tentative 定义合成一个对象，结果 4 | 没合并 → 重定义错误 |
| 静态/拒绝 | 两个 strong 函数 → 报错并点名符号，且**不产镜像** | 静默产出会让错误进镜像 |
| 静态/拒绝 | 两个 `int g = 1;` → 报错 | 同上 |
| 静态/拒绝 | 未定义 extern 仍被拒绝 | "能链就链"会出缺代码的镜像 |
| 静态/拒绝 | `.s` 输入被点名拒绝 | 让预处理器跑二进制会给一堆无意义诊断 |
| 静态/拒绝 | `-c`/`-E`/`-g`/`-link`/缺 `-o` 各一条理由 | 静默忽略等于声称做了没做的事 |
| 静态 | 无引用的 `static` 从合并程序消失，单文件编译仍在 | 剪枝过头会删掉还在用的函数 |
| 静态 | `-O2` 无 `BL one` / `-O1` 有 | 流水线跑没跑、跑几次，一次看穿 |
| 反假通过 | 单文件 `--ipo` 与普通编译的 `.s`、`.bin` **逐字节相同** | 证明差异来自合并，而不是开关本身 |
| 反假通过 | `-DARKCC_FEATURE_IPO=0` 的裁剪构建拒绝 `--ipo` | 裁剪没有藏起一个空实现 |

另外，"两个 strong 函数必须报错"这一项同时是**改名逻辑的守卫**：如果 §3.1 的改名
失效，两个 `static step` 会变成同名 strong 定义，于是静态那项会以"重复定义"变红。
换句话说，门禁里有一条检查专门负责让另一条检查失效时能被看见。

## 8. 后续（未做，写在这里避免被读成"已支持"）

1. **跨 TU 常量传播 / 全局变量定理**：合并已经把信息集中了，缺的是 pass。
2. **真对象级 LTO 的前置条件**：给 `ARKOBJ2` 增加可选的 IR 载荷段；链接期重建
   IR（需要重编号三个池）；版本兼容策略。这三件都要先在板上验证"链接器里能跑后端"。
3. **部分链接（`-r`）**：多个 `--ipo` 单元产出中间对象，最后再链接——同样卡在
   "对象里没有 IR"。
